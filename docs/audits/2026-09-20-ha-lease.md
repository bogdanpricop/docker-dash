# HA lease ownership and expiry, 20 September 2026

Status: corrected and tested in source and disposable Linux controllers on LAN
and VPS. The live application deployments remain 8.96.6 and do not yet contain
this correction. No existing Redis instance or application data was modified.

## Defects corrected

The former leader renewal used `SET leader <nodeId> XX PX 30000`. `XX` only
requires that the key exists: an old leader could overwrite a successor after
its original lease expired. A separate `GET` followed by `PEXPIRE` also allowed
an ownership race. Cached leadership had no local expiry, and concurrent first
callers could install multiple heartbeat intervals.

`cluster-lease.js` now uses one Lua transaction for acquisition/renewal. It
renews only its own value, acquires an absent key only from the reader path, and
never changes another owner's value or TTL. Shutdown compares and deletes only
its own value. The coordinator is closed before release, fencing late local
callbacks from resurrecting leadership.

Local validity is measured with a monotonic clock, from before the Redis request,
with a one-second margin subtracted from the 30-second TTL. The watchdog and
every leadership/status check expire stale state. Requests are bounded at three
seconds, and heartbeat work is single-flight. Lease coordination uses a separate
ioredis connection with offline queuing and automatic command replay disabled;
connection loss demotes the replica. General pub/sub and rate-limit connections
retain their existing behavior.

The bundled Redis profile previously used `allkeys-lru`, which could evict an
active leader key. It now uses `noeviction`; the example deployment sets the
same policy explicitly. Existing installations must apply this configuration
through their normal tested Redis rollout. This audit did not restart their Redis.

These corrections follow the ownership and lease-validity requirements in the
[Redis locking documentation](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).
They do not implement distributed fencing for external Docker/provider actions.

## Validation

- Full Jest suite: **358 suites, 4,704 passed, one omitted**. Fourteen new lease
  regressions cover stale owners, TTL preservation, atomic renewal, absent keys,
  concurrent initialization, local/watchdog expiry, delayed responses, timeouts,
  disconnects and shutdown races.
- Repository lint, JavaScript syntax and all 60 page-help checks passed.
- Fresh `npm outdated --json` returned `{}`; `npm audit --audit-level=low`
  reported zero vulnerabilities in the npm dependency tree.
- `scripts/smoke-ha-lease.js` passed ten real Redis scenarios on **both** hosts:
  independent process election, shared Lua rate limits and expiry, pub/sub without
  self-echo, stale-owner rejection, ownership-safe shutdown, disconnect demotion,
  reconnect confirmation, takeover after `SIGSTOP` exceeds the real TTL,
  immediate acquisition after graceful release, and memory-pressure rejection
  without lease eviction.

The [machine-readable proof](2026-09-20-ha-lease.json) records timestamps, image
identities, working-copy source hashes and scenarios. The controllers used the
8.96.6 application image with only the listed service/test source files replaced
inside each disposable controller. Thus this validates the changed source with
the deployed ioredis 6.0.0 dependency, not a newly built production image.

Redis bound only to loopback in its own namespace. The test controller shared
that namespace; no ports, Docker sockets or production data volumes were exposed
to it. The backend used a generated test-only password, memory/CPU/PID limits,
a read-only root filesystem and ephemeral data. All owned test containers and
their data were removed after each successful run.

The test backend was official Redis **8.10.1-alpine**, pinned to
`sha256:bd999b5cfee25fb24b8320a31fddbd69f462df44c8138c66e369582937beebc0`.
[Redis 8.10.2](https://github.com/redis/redis/releases/tag/8.10.2) is the newer
security release, but its official Docker tag returned `not found` on both hosts
at the audit time. Version 8.10.1 was used solely for the isolated compatibility
canary; it is not recommended as the new production version or declared free of
vulnerabilities. Updating and validating the bundled production Redis image
remains open.

To reproduce, pull the pinned test image and provide a verified SSH loopback
Docker forward via `DD_SMOKE_DOCKER_URL`. Set `DD_SMOKE_APP_IMAGE` to the exact
application image ID, then run `node scripts/smoke-ha-lease.js`. This creates and
removes only uniquely labeled test containers; it does not enable HA in the app.

## Remaining boundaries

Already-running jobs and external requests may outlive a lease. They need their
own durable operation identities, deduplication and recovery. A Redis restart
that loses an acknowledged lease, asynchronous replica promotion, eviction or
external lease deletion can still produce conflicting coordination histories.
No exactly-once execution or general production HA certification is claimed.

The real tests cover coordination, rate-limit Lua and pub/sub. They do not cover
shared SQLite/WAL on the user's storage, load balancer behavior, Sentinel/Redis
Cluster promotion, TLS/ACL deployment, sustained multi-replica load or every
scheduled job. The existing rate-limit middleware still fails open on Redis
errors. Those remain separate audit items. The HA reference and failover runbook
now describe the implemented lease behavior and these limitations.

## Rezumat operational

Lease-ul Redis nu mai poate fi preluat de un lider vechi prin reinnoire. Expirarea
locala, erorile de conexiune si timeout-ul retrag rolul de lider; oprirea nu poate
sterge lease-ul altei replici. Politica `noeviction` pastreaza cheia la presiune
de memorie, respingand scrierile in loc sa o elimine. Zece scenarii reale au trecut
pe fiecare host. Corectia este verificata in controllere temporare, nu instalata
inca in aplicatiile live. Operatiile externe deja pornite si failover-ul Redis cu
pierdere de date necesita protectii si verificari separate.
