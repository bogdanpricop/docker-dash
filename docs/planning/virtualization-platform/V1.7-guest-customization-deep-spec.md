# V1.7 Deep spec — structured customization and reconciliation

## Contract

`customization` schema `1.0` is additive to the V1.6 provisioning request:

```json
{
  "osFamily": "linux",
  "hostname": "app-01",
  "domain": "example.internal",
  "timezone": "Europe/Bucharest",
  "user": "deploy",
  "sshAuthorizedKeys": ["ssh-ed25519 ..."],
  "network": {
    "mode": "static",
    "interfaceName": "eth0",
    "address": "192.0.2.10/24",
    "gateway": "192.0.2.1",
    "dnsServers": ["1.1.1.1"],
    "searchDomains": ["example.internal"]
  }
}
```

Normalization is deterministic: hostname/domain are lower-cased, arrays are deduplicated, CIDR is canonicalized and missing network defaults to DHCP on `eth0`. OpenSSH payloads must be canonical base64 and embed the declared algorithm. Only public-key algorithms explicitly allowed by the schema are accepted.

## Safety boundary

- allowlisted root and network fields; unknown fields fail the request;
- Linux only, one IPv4 NIC, bounded list sizes and payload lengths;
- no password fields, private keys, `runcmd`, `bootcmd`, scripts or arbitrary YAML;
- YAML is generated from normalized objects with the maintained `yaml` library;
- API preflight returns key fingerprints, never key text;
- full request is stored only in the operation engine's encrypted payload;
- release flag and live `vm.guestCustomize` evidence are both mandatory.

## Provider translations

### Proxmox

The post-clone stage writes only `ciuser`, `sshkeys`, `ipconfig0`, `nameserver` and `searchdomain`. The operation checkpoints `customize-ready`, `customize-submit` and `customize-verify`. Recovery reads the cloned VM config; if desired state is absent, the same idempotent PUT is replayed and verified. Deadline exhaustion produces `unknown`, not a false failure.

### vSphere

The generated `CustomizationSpec` uses `CustomizationLinuxPrep`, `CustomizationGlobalIPSettings` and one `CustomizationAdapterMapping`. Static CIDR is converted to an IPv4 netmask. `CheckCustomizationSpec` runs on the source template before clone. `VirtualMachineCloneSpec` follows WSDL sequence `location`, `template`, optional `customization`, `powerOn`.

### Xen Orchestra

XO support is not assumed from product name. The client reads `/rest/v0/docs/swagger.json` and enables provisioning/customization only when the discovered pool create route declares both `cloud_config` and `network_config`. Submit uses `sync=false`, persists `taskId`, and renders Cloud-Init plus network v2 YAML. Because the VM remains off, the config-drive VDI is retained for first boot.

Direct XAPI and raw Xen remain blocked rather than synthesizing an unverified storage/upload workflow.

## Data and compatibility

No database migration is required. Existing requests without `customization` preserve V1.6 behavior and plan hashes are recomputed through the normal preflight TTL. The capability catalog addition is additive and fallback envelopes report unknown/unsupported safely.

## Failure modes

| Failure | Result |
|---|---|
| malformed schema/key/network | HTTP 400 before operation creation |
| flag off or capability absent | blocked preflight |
| vSphere spec incompatible | provider error before clone task |
| clone response lost | inventory recovery by target identity |
| Proxmox PUT response lost | read desired state; idempotent replay only if missing |
| XO task fails | durable provider task failure |
| verification deadline | operation `unknown` with bounded safe evidence |
