# V4.4g — Network MTU mismatch detector assumption audit

| Assumption | Evidence / decision | Result |
|---|---|---|
| Matching endpoint MTUs prove the whole path | An intermediate switch, tunnel or transport can have a smaller MTU | Rejected; every ordered segment is evaluated |
| VXLAN always costs exactly 50 bytes | Address family, options and nested encapsulation change overhead | Rejected; adapters provide explicit cumulative overhead inputs |
| A configured MTU proves traffic can traverse it | Routing, policy and physical behavior are independent | Rejected; pass is configuration evidence only |
| Missing MTU may inherit a safe default | Provider defaults and jumbo-frame policy vary | Rejected; missing evidence is unknown |
| DF behavior may be assumed from platform type | Guest, tunnel and network devices can alter DF semantics | Rejected; required DF needs explicit evidence |
| The detector should discover paths with probes | Active probes expand destination, traffic and privilege risk | Rejected; B120 is passive and B119 remains separate |
| Storage and migration paths can use workload defaults | They frequently use dedicated fabrics and jumbo-frame policies | Rejected; purpose and desired payload MTU are path-specific |
| The detector may remediate a mismatch | MTU changes can disconnect management, storage or migration traffic | Rejected; no mutation or remediation endpoint |
