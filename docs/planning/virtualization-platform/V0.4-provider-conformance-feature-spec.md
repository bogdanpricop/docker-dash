# V0.4 Feature spec — Provider conformance kit

## Obiectiv

Providerii Proxmox, vSphere și Xen trebuie să poată fi evaluați prin același contract automat înainte ca o capabilitate să fie promovată sau folosită de operații mutabile. Rezultatul este persistent, explicabil, host-scoped și nu expune credentiale ori referințe native.

## Scope

- manifest versionat per provider cu ownership, variante, familii API, release ring și deprecations;
- compatibility registry fără afirmații neverificate despre versiuni reale;
- circuit breaker per endpoint, half-open probe și buget bounded de concurență;
- corpus sanitizat de fixtures pentru PVE, vSphere și variantele Xen XO/XAPI/raw;
- fake adapters pentru timeout, auth expiry, partial response, redirect și task loss;
- runner de contract static, reutilizabil de pluginuri;
- certificare live read-only pentru capabilities și inventory;
- persistență run/check, scoring, grade și evidence hash determinist;
- API admin pentru pornire și API host-scoped pentru rezultate;
- scorecard automat per provider și export JSON portabil;
- metrici low-cardinality și audit pentru rulările live.

## Anti-scope

- nicio mutation pe hypervisor;
- nicio probă disposable implicită;
- nicio afirmație „certified” pentru versiuni fără fixture sau endpoint real;
- canary/wave rollout și post-action verification nu execută operații în acest batch; kit-ul doar publică și verifică cerințele lor de contract;
- DR complet al aplicației rămâne un flux separat; V0.4 oferă exportul portabil al evidenței de conformance.

## User stories

1. Un administrator vede compatibilitatea declarată și ring-ul fiecărui provider.
2. Un administrator rulează o certificare read-only pe un endpoint permis și primește checks, scor și hash.
3. Un operator cu acces la host poate citi rezultatele, dar nu poate lansa certificarea.
4. Un autor de adapter rulează același contract pe fixtures și fake failures înainte de integrare.
5. Produsul poate genera un scorecard shipped/partial/planned cu evidence către ultimul run.

## Criterii de acceptare

- manifestele built-in trec validarea strictă;
- toate cele 29 capability keys sunt prezente în contractul rezultat;
- fixture corpus acoperă cei trei provideri și cele cinci scenarii de fault;
- timeout-ul este bounded, circuitul se deschide și permite un singur half-open probe;
- live suite este numai read-only și respectă host access/RBAC;
- același evidence produce același SHA-256;
- output-ul/API-ul nu conține parole, token-uri, cookie-uri sau native refs;
- migrarea este aditivă și rollback-ul aplicației precedente ignoră noile tabele.
