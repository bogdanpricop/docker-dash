# V3.3 — Backup execution and verification feature specification

**Status:** implemented; validation and staged rollout in progress

**Release gate:** `DD_PROVIDER_BACKUP_EXECUTION=false` by default

**Provider mutation scope:** Proxmox VE `vzdump` only

**Safety boundary:** backup creation is allowed after two independent gates; retention deletion remains unavailable

## Outcome

V3.3 turns an accepted V3.2 plan into a durable parent execution containing one durable `vm.backup` operation per selected workload. Every mutation is revalidated against current Proxmox VM and repository inventory, tracked by native UPID, and accepted as successful only after V3.1 observes a new canonical recovery point that was not in the execution baseline.

Execution authorization is not inferred from policy authoring:

1. the deployment must enable `DD_PROVIDER_BACKUP_EXECUTION`;
2. an administrator with host `operate` access must type the exact policy name and select `manual` or `scheduled` authorization;
3. each manual run repeats exact-name confirmation and supplies an `Idempotency-Key`;
4. the accepted plan hash must still match a new live preflight;
5. provider capability, consistency, repository, execution window, verification, scope, and inventory completeness checks must pass.

Xen Orchestra, XAPI, raw Xen, vSphere, and ESXi remain fail-closed for backup mutation. Their read-only recovery-point inventories are unchanged.

## User stories

1. An administrator can authorize manual execution without enabling unattended schedules.
2. An administrator can separately authorize scheduled execution only for an enabled planning policy.
3. Repeating a request with the same idempotency key returns the original parent execution and never submits a second provider task.
4. A scheduled plan is revalidated immediately before any child operation is created.
5. The configured concurrency limit bounds active provider backup tasks while completed backups wait independently for verification.
6. A successful Proxmox task without a newly observed recovery point becomes `unknown`, never `succeeded`.
7. Required verification remains `verification_pending`, then becomes `succeeded`, `failed`, or `unknown` from live repository evidence.
8. Cancellation stops queued/running work where possible but never removes already created recovery points.
9. A viewer can inspect executions, item states, canonical recovery-point IDs, and verification state without seeing provider-native references.

## Functional contract

### API

| Method | Path | Access | Effect |
|---|---|---|---|
| `GET` | `/api/providers/:hostId/backup-policies/executions` | host viewer | list parent executions and child evidence |
| `GET` | `/api/providers/:hostId/backup-policies/executions/:executionId` | host viewer | inspect one host-scoped execution |
| `POST` | `/api/providers/:hostId/backup-policies/:policyId/execution-authorization` | admin + operate + writeable | set `disabled`, `manual`, or `scheduled` authorization |
| `POST` | `/api/providers/:hostId/backup-policies/:policyId/execute` | admin + operate + writeable | create/reuse an idempotent manual execution |
| `POST` | `/api/providers/:hostId/backup-policies/executions/:executionId/cancel` | admin + operate + writeable | cancel queued/running children; preserve completed backups |

All responses use schema `1.0`. Error codes and details are bounded and sanitized. Native VM references, storage IDs, UPIDs, credentials, encryption keys, repository URLs, and upstream error text are not exposed in public execution objects.

### Persistent model

Migration `119_provider_backup_execution` adds:

- fail-closed `execution_mode` and authorization evidence to `provider_backup_policies`;
- `provider_backup_executions` for accepted plan, trigger, idempotency request hash, state, counts, actor, and timestamps;
- `provider_backup_execution_items` for workload, durable operation, immutable baseline hash, canonical recovery point, verification state, and error code.

The parent has a unique plan-run relation and policy-scoped idempotency key. Each workload appears once per execution and each child operation can belong to only one item.

### State model

Parent states:

```text
queued → running → verification_pending → succeeded
              ├──────────────────────────→ partial
              ├──────────────────────────→ failed
              ├──────────────────────────→ cancelled
              └──────────────────────────→ unknown
```

Item states:

```text
queued → running → verification_pending → succeeded
          ├──────────────────────────────→ failed
          ├──────────────────────────────→ cancelled
          └──────────────────────────────→ unknown
```

`partial` is parent-only and means at least one workload succeeded while another ended unsuccessfully. A recovery point with `failed` verification is a failed item. An unverified point past the policy deadline is `unknown`.

## Proxmox translation

- canonical `qemu/<vmid>` or `lxc/<vmid>` identity is resolved server-side;
- current node, guest type, template/lock state, and repository accessibility are reread live;
- node-local `storage@node` repositories must match the VM's current node;
- one `POST /nodes/{node}/vzdump` call is submitted with one VMID, explicit storage, snapshot mode, zstd compression, and an optional bounded KiB/s limit;
- the returned UPID is encrypted by the existing operation engine and polled through the task status endpoint;
- provider success starts recovery-point discovery; it does not finish the item by itself;
- the new point must be outside the baseline, scoped to the same repository/workload, and temporally plausible;
- retention evaluation remains advisory and every result carries `retentionMutationAuthorized:false`.

The implementation supports the common minimum of crash-consistent semantics. Policies requesting filesystem/application consistency are rejected at execution time because the current transport cannot prove those guarantees uniformly per workload.

## Source-derived requirements

- Proxmox VE exposes node-scoped backup execution through `vzdump`, with VMID, storage, mode, compression, and bandwidth options: [Proxmox VE API viewer](https://pve.proxmox.com/pve-docs/api-viewer/index.html#/nodes/{node}/vzdump) and [current administration guide](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#chapter_vzdump).
- Proxmox documents bandwidth limits in KiB/s; the common Mbps policy is translated explicitly rather than passed through with ambiguous units: [Proxmox VE command reference](https://pve.proxmox.com/pve-docs/vzdump.1.html).
- PBS verification reads and validates backup data independently of task completion, so verification is a separate state and deadline: [PBS verification documentation](https://pbs.proxmox.com/docs/maintenance.html#verification).
- PBS prune removes snapshot metadata before later garbage collection and therefore is not bundled into backup success: [PBS pruning documentation](https://pbs.proxmox.com/docs/maintenance.html#pruning).
- The current Xen Orchestra REST backup-job controller exposes read routes, while mutation is available through a distinct JSON-RPC surface. Docker Dash does not silently substitute an undiscovered transport: [XO REST controller](https://github.com/vatesfr/xen-orchestra/blob/master/%40xen-orchestra/rest-api/src/backup-jobs/backup-job.controller.mts) and [XO `backupNg` API source](https://github.com/vatesfr/xen-orchestra/blob/master/packages/xo-server/src/api/backup-ng.mjs).

## Acceptance criteria

- migration is additive, defaults execution to disabled, and enforces state/identity/idempotency constraints;
- authoring or planning alone cannot start a provider mutation;
- authorization requires the release flag, admin + host operate, global writeability, and exact-name confirmation;
- manual submit requires a bounded visible-ASCII idempotency key;
- duplicate requests reuse the original execution; conflicting reuse returns `409`;
- a current live plan must equal the accepted plan hash before dispatch;
- execution fails closed for non-Proxmox providers, truncated baseline, unsupported consistency/disk exclusion, closed window, or unproven required verification;
- child operations hold VM and repository locks and never replay a non-idempotent mutation after an ambiguous response;
- native task completion without new recovery-point evidence yields `unknown`;
- required verification is polled separately and never inferred from repository type alone;
- cancellation is durable and cannot delete completed backup data;
- active policy definitions cannot be changed or deleted;
- route, handler, service, adapter, migration, client, UI, full-suite, lint, staging migration, HTTP, database, and container checks pass.

## Explicit non-goals

- retention prune, garbage collection, backup deletion, or repository mutation;
- XO JSON-RPC/WebSocket backup execution without a dedicated conformance-tested transport;
- vSphere/ESXi backup execution;
- raw XAPI/xl/xm backup orchestration;
- guest application hooks or a portable claim of filesystem/application consistency;
- file, disk, or VM restore (V3.4);
- automated restore drills (V3.5);
- replication, failover, or failback (V3.6);
- storing or transmitting encryption key material.
