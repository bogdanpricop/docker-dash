# V1.3.2 Deep spec — Snapshot policy orchestration

## Model persistent

Migration 111 adaugă `provider_vm_snapshot_policies` și `provider_vm_snapshot_policy_runs`. Policy este unică pe `(host_id, vm_id)`. Ștergerea policy este soft-delete, astfel încât run evidence rămâne disponibil și policy poate fi recreată controlat. Run-ul are slot unic per policy, stare, plan public bounded, child operation curent, număr de delete confirmate și eroare sanitizată.

Stări run: `previewed`, `create_pending`, `retention_pending`, `succeeded`, `blocked`, `failed`, `unknown`. `create_pending` și `retention_pending` sunt reluate la fiecare tick din starea `provider_operations`; nu se păstrează provider refs în policy tables.

## Scheduling

Job-ul rulează în fiecare minut prin wrapper-ul existent leader-only/no-overlap. Sloturile sunt UTC și folosesc trei forme portabile:

- hourly: minute `0`, `15`, `30` sau `45`;
- daily: hour `0..23` plus minute;
- weekly: weekday `0..6`, hour și minute.

`UNIQUE(policy_id, slot_key)` și `last_slot_key` dedupează restart, HA handover și tick repetat. Node-cron este doar wake-up; due state și orchestration sunt în SQLite.

## Plan retention

Un snapshot este managed numai dacă numele începe exact cu `<prefix>-`. Snapshot-urile managed se sortează după `createdAt` desc. Primele `retainCount` sunt protejate. Restul devin candidate numai dacă:

- au timestamp valid și, când este configurat, sunt mai vechi de `maxAgeDays`;
- `isCurrent=false`;
- `childCount=0`;
- integrity este `valid`;
- nu depășesc `maxDeletesPerRun`.

Orice snapshot fără ownership prefix este manual și nu intră în candidate. Planul public conține doar ID canonic, nume, timestamp și reason.

## Orchestration

1. live inventory + policy evaluation;
2. dry-run: persistă `previewed`, fără child operation;
3. execute: submit create cu nume `<prefix>-YYYYMMDDHHmm`, plan hash și idempotency key determinist;
4. tick ulterior citește child operation;
5. după create success, refresh live și recalculează retention;
6. submit cel mult un leaf delete;
7. după fiecare delete success, refresh/recalc și continuă până la limită;
8. child failed/cancelled/unknown propagă terminal fail-closed în policy run.

Nu există apel direct la provider din scheduler și nicio mutație nu este retrimisă.

## API

- `GET /api/providers/:hostId/virtual-machines/:vmId/snapshot-policy`
- `PUT /api/providers/:hostId/virtual-machines/:vmId/snapshot-policy`
- `DELETE /api/providers/:hostId/virtual-machines/:vmId/snapshot-policy`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshot-policy/preview`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshot-policy/run`
- `GET /api/providers/:hostId/virtual-machines/:vmId/snapshot-policy/runs`

CRUD/run cer admin, effective host `operate` și writeable mode. Read/history cer host `view`. Preview poate rula cu policy salvată sau draft bounded. Execute enable și run manual cer typed VM name.

## Defaults

- feature gate execute: false;
- policy: disabled, dry-run;
- daily 02:15 UTC;
- crash consistency;
- prefix `dd-auto`;
- retain 3;
- max age 3 days;
- maximum 2 deletes per policy run.

Defaulturile sunt conservatoare: Broadcom recomandă 2–3 snapshot-uri și maximum 72 ore pentru vSphere, iar XAPI VMSS modelează explicit frecvență și retained snapshot count. Aceste valori sunt guardrails, nu afirmații de backup/recovery.
