# V4.4i — Load balancer inventory

**Backlog:** B123
**Status:** local implementation complete; browser/provider collectors/release pending
**Scope:** normalized read-only load-balancer evidence

## Outcome

Administrators can import immutable load-balancer observations with VIPs,
listeners, pools, members, algorithms, provider-reported health and canonical
provider/network/resource links. The inventory gives one bounded contract for
future NSX, OpenStack Octavia, cloud and connector adapters.

## Contract and state

- A batch declares source, provider host/type, observation/expiry and coverage.
- Each load balancer has a canonical key, scope, provider state, VIP addresses,
  listener and pool definitions, plus opaque canonical link keys.
- Listener default-pool references and member identities are validated inside
  the batch; duplicate keys and dangling pool references are rejected.
- Health is provider/imported evidence only. Unhealthy members and degraded
  provider state remain visible; incomplete, expired or unknown evidence is
  `unknown`, never healthy by default.
- Native references, provider URLs, credentials and raw health payloads are not
  accepted.

## Persistence and UI

- Observations are immutable, bounded and SHA-256 deduplicated.
- Admin-only audited ingestion is exposed under Network Advanced.
- UI reports LB/VIP/listener/pool/member totals, healthy/unhealthy/unknown
  members, coverage/freshness and immutable evidence hashes.

## Safety

- No listener, pool, member, VIP or health-check mutation.
- No packet, socket, HTTP request, DNS lookup, provider call or active probe.
- B124 address lifecycle and any future LB mutation remain separate guarded
  workflows.

## Acceptance evidence

- multi-VIP, listener/pool/member normalization and summaries;
- dangling/duplicate reference rejection;
- provider degraded/error and member health classification;
- incomplete/expired evidence fail-closed;
- strict secret rejection, dedupe, API audit, UI and registry reconciliation.
