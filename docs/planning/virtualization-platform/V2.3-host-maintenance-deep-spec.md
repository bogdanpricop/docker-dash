# V2.3 — Host maintenance deep spec

## Persistence

Migration 114 adds three additive tables:

- `provider_host_maintenance_runs`: immutable approved plan, state machine, native task reference, lease, owner and error evidence;
- `provider_host_maintenance_items`: one row per planned VM with sequence, selected target/mode and child operation;
- `provider_host_maintenance_events`: append-only bounded public progress evidence.

The reviewed plan and native task reference are encrypted with the existing application encryption key. Their SHA-256 hashes are stored separately for integrity/correlation. A partial unique index permits only one active reservation per endpoint/source host. The migration has no destructive rewrite and old application versions ignore the new tables.

## Plan algorithm

1. Read canonical host and VM inventory from the selected endpoint.
2. Reject transient source identity, offline source, unsupported provider plane or more than 200 managed VMs.
3. For every VM, obtain fresh V2.1 migration evidence and resolve its current canonical host.
4. Keep VMs whose source equals the selected host.
5. Exclude current, offline, disabled, provider-maintenance and Docker-Dash-reserved targets.
6. Prefer `live` for running VMs and `cold` for stopped VMs. Other states remain non-migratable.
7. Score eligible candidates by provider score and remaining memory after the common 10% VM-memory reserve. Deduct each assignment from the target's planning budget.
8. Persist no read-only plan. Return a semantic hash whose projection excludes response-only timestamps but includes identities, placement, modes, blockers and expiry.

`nonMigratablePolicy=block` makes submission impossible. `defer` allows an evacuation run to migrate eligible VMs, then pause with the deferred list; it never permits native maintenance entry while a workload remains.

## Worker and restart behavior

The existing leader-gated background job calls `runDue()` every minute. Route submission and resume also call one immediate reconciliation pass for responsive dispatch. Each run has a short SQLite lease, so a duplicate scheduler cannot launch a second wave.

For each pass:

1. reclaim an expired run lease;
2. reconcile submitted children from `provider_operations`;
3. stop on any `failed`, `cancelled` or `unknown` child and persist `paused`;
4. re-read placement for children apparently completed outside Docker Dash;
5. dispatch at most `waveSize - activeChildren` new children;
6. once every item succeeded, refresh inventory and require the source count to be zero;
7. for `drain`, settle in `drained` with the reservation retained;
8. for `enter`, submit exactly one native task, reconcile it, then verify provider state before `maintenance`;
9. release the lease in all paths.

Idempotency keys are derived from `maintenance:<runId>:<vmId>` and therefore survive restart. The child operation engine remains authoritative for locks, cancellation and no-replay semantics.

## Native provider bridge

### vSphere

- `enterHostMaintenance(hostRef)` calls `EnterMaintenanceMode_Task` with a bounded timeout and `evacuatePoweredOffVms=false`.
- `exitHostMaintenance(hostRef)` calls `ExitMaintenanceMode_Task`.
- task reconciliation uses the existing vSphere Task reader and conditional `CancelTask` support.
- post-check requires `runtime.inMaintenanceMode=true/false` as appropriate.

### XAPI

- preparation submits `Async.host.disable` before migration waves, preventing new VM starts on the source;
- the disabled state is the native maintenance boundary after the host is empty;
- exit submits `Async.host.enable`;
- `host.get_record` supplies the live `enabled` and resident VM evidence;
- raw Xen and undiscovered XO actions fail closed.

### Proxmox

The supported goal is `drain`. VMs are evacuated through durable V2.2 tasks and the local source reservation stays active until exit. Docker Dash does not invoke undocumented REST paths or SSH CLI fallbacks for HA node maintenance. A later capability probe may add native activation when an official versioned API is both available and conformance-tested.

## Cancellation

- `queued`, `preparing`, `draining` or `paused`: set cancel intent, stop new dispatch and request child cancellation where supported;
- if no active child remains, settle `cancelled`; local reservation is released;
- after `drained` or `maintenance`, cancellation is rejected and explicit `exit` is required;
- a native task with an uncertain cancellation result moves the run to `unknown`.

## Observability

Public run projection includes counts (`pending`, `active`, `succeeded`, `blocked`, `failed`, `unknown`), current wave, safe events, timestamps and child operation IDs. It excludes raw provider references and encrypted payloads. Audit actions use the prefix `provider_host_maintenance_`.

- semantic plan hashing and expiry;
- aggregate target capacity and reserved-target exclusion;
- blocked versus deferred workload behavior;
- idempotent submission and active-run uniqueness;
- wave concurrency, restart recovery and child reconciliation;
- auto-pause on failure/unknown;
- empty-host post-check and placement-race detection;
- vSphere/XAPI native submit, task poll and post-state validation;
- Proxmox drain-only and raw/XO fail-closed behavior;
