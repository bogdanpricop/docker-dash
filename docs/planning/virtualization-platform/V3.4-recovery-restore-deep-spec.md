# V3.4 — Recovery restore deep specification

## 1. Invariants

- Restore is conceptually and operationally separate from snapshot revert and backup creation.
- A canonical recovery-point ID is the public source identity; native archive references stay encrypted at rest.
- The destination is create-only. Existing VMIDs are never overwritten, even when the provider API supports `force`.
- Restored guests remain powered off. Instant/live restore is not an alias for full restore.
- Restored QEMU/LXC network identities are randomized by the provider. Network mappings are inherited but cannot transmit while the guest remains stopped.
- No automated cleanup follows failed, cancelled, or ambiguous restore because PVE documents that data/config may be partially present.
- No retry may repeat the provider mutation. Reconciliation uses a durable pre-submit checkpoint, native UPID, target identity, and live inventory.

## 2. Capability contract

| Capability | Proxmox V3.4 | Xen/XO V3.4 | vSphere/ESXi V3.4 |
|---|---|---|---|
| `backup.restore.vm` | conditional, task-backed | unsupported until JSON-RPC transport is conformance-tested | unsupported |
| `backup.restore.disk` | unsupported | unsupported | unsupported |
| `backup.restore.file` | unsupported | unsupported despite upstream availability | unsupported |
| `backup.restore.instant` | unsupported | unsupported | unsupported |
| `backup.restore.differential` | unsupported | unsupported despite upstream availability | unsupported |

Upstream product support is not sufficient evidence that the current Docker Dash adapter can mutate safely.

## 3. Plan inputs and validation

The service resolves and re-reads:

1. the host-scoped canonical recovery point and encrypted archive reference;
2. its canonical repository and current provider inventory;
3. the requested canonical target node and storage identities;
4. live node availability and node-local storage status/content types;
5. live VM inventory for target VMID conflicts;
6. active durable restore locks;
7. provider capability and global operation policy.

VMID must be an integer from 100 through 999,999,999. The target node/storage identities must belong to the same endpoint. QEMU requires `images`; LXC requires `rootdir`. When known free capacity is below known recovery-point size, execution is blocked. Unknown size/capacity is a warning and execution-time storage validation remains mandatory.

Verification rules:

| State | Default | Override |
|---|---|---|
| verified | allowed | not required |
| failed | blocked | forbidden |
| stale/unverified/unknown | blocked | `allowUnverified=true`, bounded reason, stronger confirmation |

Plan validity is five minutes. Its semantic hash includes source point/repository/type/size/verification, target canonical IDs/VMID/content/capacity, override evidence, blockers/warnings, capability state, and policy result. Observation time and expiry time are excluded.

## 4. Confirmation and authorization

- preflight: authenticated administrator with host `operate` access;
- submit: the same plus global writeability;
- verified confirmation: `RESTORE <vmid>`;
- override confirmation: `RESTORE UNVERIFIED <vmid>`;
- idempotency key: 8–200 visible ASCII characters;
- override reason: 20–240 printable characters after control-character removal.

Changing any semantic input requires a new plan and hash. Idempotency reuse with different intent is a conflict in the common operation engine.

## 5. Durable operation

Operation type is `vm.restore`, with the recovery point as its canonical resource. Lock scopes cover the recovery point, target VMID, target node, and target storage.

```text
queued
  → running/pre-submit-checkpoint
  → reconciling/native-task
  → reconciling/post-verify
  → succeeded

Any ambiguous submit/task/post-state → unknown
Provider/task failure               → failed
Confirmed native cancellation       → cancelled (manual inspection required)
```

Before the provider call, the handler persists a non-native checkpoint containing only provider, target node, guest type, and VMID. If execution resumes from this checkpoint, it searches for the target and never resubmits. After submission the checkpoint is replaced by encrypted UPID evidence.

## 6. Provider translation

QEMU:

```text
POST /api2/json/nodes/{node}/qemu
vmid=<new>; archive=<server-resolved>; storage=<server-resolved>
force=0; unique=1; start=0; live-restore=0; bwlimit=<optional KiB/s>
```

LXC:

```text
POST /api2/json/nodes/{node}/lxc
vmid=<new>; ostemplate=<server-resolved>; storage=<server-resolved>
restore=1; force=0; unique=1; start=0
```

The source archive must still appear in live recovery-point inventory. A node-local repository must match the target node. Shared repositories may restore to a node on which the source and selected destination storage are active.

## 7. Post-verification and failure semantics

Success requires live normalized VM inventory to contain exactly the requested VMID/type on the requested node and report a non-running power state. The public result contains only canonical target ID, display name, power state, target VMID, source recovery-point ID, and safety flags.

When the native task fails, cancellation succeeds, or the result cannot be proven, the operation result/error explicitly states `partialTargetMayExist:true`, `automaticCleanupAuthorized:false`, and `startAfterRestore:false`. The operator must inspect PVE before any deletion or retry with another VMID.

## 8. Deferred slices

- file browse/download needs a bounded streaming contract, archive/partition path validation, content-disposition hardening, quotas, and no server-side extraction path;
- disk restore needs destination disk ownership, attach mode, guest state, and rollback semantics;
- XO restore needs authenticated JSON-RPC discovery, task identity, post-create matching, and token/session isolation;
- differential and instant restore need provider-specific base-chain and isolation proofs;
- automated boot/app validation and cleanup belong to V3.5.
