# V6.4a — VM observability and event correlation

**Release:** v8.53.0
**Backlog:** B206–B215

## Scope

V6.4a builds bounded read and advisory workflows over the canonical VM metric
schema introduced by V4.6c. It adds performance comparison, contention/storage/
network views, normalized event evidence, correlation, topology impact and
multi-signal rules. It does not enable a background provider collector and does
not authorize a provider mutation.

## Contracts

- Performance queries require 1–10 resources and 1–12 metrics, allow at most
  31 days and 20,000 source points, and downsample each returned series to 500
  points. Event annotations share the same resource/time boundary.
- The canonical metric catalog adds CPU ready/steal, balloon/swap, storage
  operation/latency/queue/resync and network error/drop/flow/MTU series.
  Unsupported evidence remains absent rather than being represented as zero.
- Contention, storage and network dashboards derive bounded counter rates and
  keep the underlying values and labels in every row. Noisy-neighbor evidence
  is reported only when resources share an explicit host/node/cluster label.
- Event ingestion accepts at most 5,000 observations from a declared adapter.
  vSphere watch, XAPI events, PVE log/task poll, Azure Event Grid, generic
  webhook and generic poll normalize to one local schema.
- Native IDs deduplicate within provider-host/adapter scope. Events without an
  ID use a SHA-256 fingerprint and a configurable 1–86,400 second window.
  Duplicates increment `repeat_count` and preserve the first evidence row.
- Opaque/sequence/timestamp/resource-version cursors are stored only after the
  complete event batch commits.
- The correlation timeline merges normalized events, audit changes, existing
  alerts and metric evidence. The VM incident view filters lifecycle and alert
  context without claiming root cause.
- Topology edges point from upstream dependency to downstream consumer.
  Impact traversal is cycle-safe, limited to four hops and 500 results.
- Multi-signal rules require 2–8 conditions spanning at least two of metric,
  event and collection state. Evaluations retain each condition's value,
  threshold and duration result; alerts are advisory and locally resolved.

## UI and API

The Governance page includes a dedicated Observability tab with the three
performance dashboards, event evidence, topology/alert summary, a Chart.js
comparison modal and forms for event ingestion, topology edges and metric+event
rules. All mutation endpoints use the existing read-only/writeability guard and
audit log.

API root: `/api/governance/lifecycle/observability`.

## Verification

Tests cover metric catalog expansion, compare/annotation results, all three
dashboards, event cursor and deduplication, correlation/incident timelines,
bounded topology propagation and explainable multi-signal alert creation.
