# V2.6 — Placement and HA mutation feature specification

**Status:** implementation-ready
**Backlog:** B068, B070, B073
**Depends on:** V0.3, V2.2, V2.4, V2.5
**Scope:** approved HA-policy changes, approved affinity-rule changes, and controlled rebalance apply

## User outcome

An administrator can prepare a provider-neutral change, inspect the current and desired state as a semantic diff, request a second administrator's approval, and execute it through durable operations. Rebalance apply executes bounded VM migrations in waves and automatically pauses when live evidence no longer matches the approved plan. A completed policy change can produce a new approval request that semantically restores the captured before-state.

## Safety contract

1. Planning never mutates a provider.
2. The requester cannot approve or reject their own request.
3. Approval re-reads provider state and rejects stale or expired plans.
4. Approval creates exactly one durable parent operation using an idempotency key.
5. Provider policy changes use incremental APIs and post-read verification.
6. Rebalance re-runs migration preflight immediately before every child operation.
7. At most five changes and at most two VM migrations execute concurrently by default.
8. A failed, cancelled, unknown, or stale child automatically pauses a rebalance.
9. Cancellation never silently migrates completed VMs back.
10. Rollback is a new semantic plan and needs independent four-eyes approval.
11. Provider-native references are encrypted at rest and never returned by the API.
12. A transport failure after native submission is `unknown` until task/state reconciliation.

## Portable mutations

### HA policy

The common model is deliberately sparse. Unsupported fields are rejected rather than ignored.

| Field | Meaning | Provider mappings |
|---|---|---|
| `restartPolicy` | `disabled`, `best_effort`, or `guaranteed` | Proxmox HA membership/state; vSphere HA override; Xen `ha_restart_priority` |
| `restartPriority` | `default`, `lowest`, `low`, `medium`, `high`, `highest` | vSphere DAS priority; advisory mapping for other providers |
| `maxRestarts` | same-node restart attempts | Proxmox `max_restart` |
| `maxRelocations` | relocation attempts after restart exhaustion | Proxmox `max_relocate` |
| `startOrder` | dependency start group | Xen `order` |
| `startDelaySeconds` | delay before the next start group | Xen `start_delay` |

The capability envelope lists the writable fields for the concrete endpoint. V2.6 does not enable or disable cluster-wide HA and does not change admission-control capacity.

### Affinity rules

Portable rule kinds are `vm_vm_affinity`, `vm_vm_anti_affinity`, `vm_host_affinity`, `vm_host_anti_affinity`, and `home_host_preference`. Each request uses canonical VM/host/cluster IDs, a stable rule name, an enabled flag, and a mandatory flag where the provider supports it.

- Proxmox VE 9+: resource-affinity and node-affinity rules.
- vCenter: VM affinity/anti-affinity DRS rules in V2.6; VM/host groups remain read-only until group lifecycle passes conformance.
- XenServer/XCP-ng XAPI: anti-affinity VM groups and VM home-server affinity.
- Xen Orchestra mutation, standalone ESXi, Proxmox VE 8, and raw Xen: unsupported with an explicit capability reason.

### Rebalance apply

The apply request includes V2.5 thresholds, maximum moves, wave size, stop policy, maintenance window, and the V2.5 advisory hash. V2.6 recomputes the advisory before creating the approval request and again before approval. Each move is persisted independently and invokes the V2.2 migration workflow; no provider DRS recommendation is blindly applied.

## API

- `POST /api/providers/:hostId/placement/changes/preflight`
- `POST /api/providers/:hostId/placement/changes`
- `GET /api/providers/:hostId/placement/changes`
- `GET /api/providers/:hostId/placement/changes/:changeId`
- `POST /api/providers/:hostId/placement/changes/:changeId/approve`
- `POST /api/providers/:hostId/placement/changes/:changeId/reject`
- `POST /api/providers/:hostId/placement/changes/:changeId/pause`
- `POST /api/providers/:hostId/placement/changes/:changeId/resume`
- `POST /api/providers/:hostId/placement/changes/:changeId/cancel`
- `POST /api/providers/:hostId/placement/changes/:changeId/rollback/plan`

All mutation routes require authentication, administrator role, endpoint `operate` access, CSRF protection, an `Idempotency-Key`, typed confirmation, and an audit event. List/detail access remains endpoint-scoped and admin-only in V2.6.

## Persistent state

`provider_placement_changes` stores the encrypted request, approved plan, captured before-state, semantic rollback input, approval identities, operation link, lease, state, and bounded errors. `provider_placement_change_items` stores one durable rebalance move and child operation. `provider_placement_change_events` stores the append-only workflow history.

States are `pending_approval`, `approved`, `applying`, `paused`, `verifying`, `succeeded`, `rejected`, `cancelled`, `failed`, `unknown`, `rolling_back`, `rolled_back`, and `rollback_failed`.

## Feature flags and limits

- `DD_PROVIDER_HA_POLICY_MUTATION=false`
- `DD_PROVIDER_AFFINITY_MUTATION=false`
- `DD_PROVIDER_REBALANCE_APPLY=false`
- `DD_PROVIDER_PLACEMENT_CHANGE_CONCURRENCY=2`
- `DD_PROVIDER_PLACEMENT_CHANGE_MAX_MOVES=20`
- `DD_PROVIDER_PLACEMENT_CHANGE_APPROVAL_TTL_MS=900000`

The three mutation flags are independent so rollout can enable only the surface that has real endpoint evidence.

## Audit actions

`provider_placement_change_preflight`, `provider_placement_change_requested`, `provider_placement_change_approved`, `provider_placement_change_rejected`, `provider_placement_change_paused`, `provider_placement_change_resumed`, `provider_placement_change_cancelled`, and `provider_placement_change_rollback_requested` include endpoint ID, change ID, kind, semantic plan hash, operation ID when present, and actor ID. Native refs and full plan bodies are excluded.

## Acceptance criteria

- a request cannot self-approve and stale approval produces no operation;
- plan hashes are stable across timestamps and change when semantic before/desired state changes;
- all provider mutations are post-read verified;
- unsupported provider/version/field combinations fail before a request can be created;
- rebalance persists child state, wave, operation ID, pause reason, and restart recovery;
- rollback planning reads current state and never replays an old native payload;
- route/RBAC/audit, migration, provider contract, fault, and page tests are green;
- rollout keeps all mutation flags disabled unless a disposable real target is available.
