# V4.4e — Network dependency map assumption audit

| Assumption | Evidence / decision | Result |
|---|---|---|
| A successful flow proves an application dependency | A flow proves communication only; scans, health checks and incidental traffic are common | Rejected; flow edges are non-causal candidates |
| An IP address always identifies one VM | NAT, stale guest tools, anycast and conflicts can produce multiple owners | Rejected; resolve only unique current ownership |
| DNS records prove that a client consumes a service | DNS expresses name/address mapping, not client usage | Rejected; DNS only annotates correlated nodes |
| Every metadata string may contain a dependency | Arbitrary parsing would create uncontrolled false positives | Rejected; only exact dependency schema keys are eligible |
| Confidential metadata can appear in map evidence | Map/API exposure broadens its audience and retention | Rejected; confidential values are excluded |
| Old edges should be dropped | Operators need to distinguish stale from absent evidence | Rejected; retain within source retention and label freshness |
| Observed candidates may participate in blast-radius traversal | This would convert correlation into causality | Rejected; impact traversal uses declared edges only |
| Building the map requires active network probes | Existing normalized evidence is sufficient for this feature slice | Rejected; zero network calls and mutations |
