# V2.1c — Scheduled VM actions

**Backlog:** B045
**Status:** implementation in progress
**Scope:** common provider VM inventory and durable operation core

## Outcome

Administrators can attach multiple durable schedules to a VM for `start`,
`stop`, `reboot`, or `snapshot`. A schedule uses a five-field cron expression
in an IANA timezone, records every eligible decision, and dispatches at most one
provider operation for a due wall-clock slot across restarts and HA leader
handover.

## Safety contract

- New schedules are disabled and `dry_run` by default.
- `stop` maps to the existing guest-aware `shutdown` operation. Forced power is
  deliberately excluded from scheduled actions.
- Execute mode requires the exact current VM display name and the dedicated
  `DD_PROVIDER_VM_ACTION_SCHEDULES` release flag. The underlying power or
  snapshot release flag must also allow the provider preflight.
- Targets are canonical stable VM IDs captured at authoring time; dynamic
  selectors are not accepted.
- Every execution reruns the existing provider inventory, capability, policy,
  state, and conflict preflight. The scheduler cannot bypass operation locks.
- Snapshot schedules only create a snapshot. They do not imply backup,
  retention, consolidation, revert, or delete.
- Scheduled runs never use emergency blackout overrides. Both recurring local
  blackout windows and active governance blackout windows suppress dispatch.
- Missing targets, provider/preflight failures, active-operation conflicts and
  unknown outcomes remain explicit run evidence. Consecutive terminal failures
  disable a schedule at its configured threshold.

## Persistence and concurrency

- `provider_vm_action_schedules` stores the target, cron, timezone, DST policy,
  execution mode, optimistic version, safety confirmation and failure state.
- `provider_vm_action_schedule_runs` stores an immutable due-slot key, local
  wall time, DST occurrence, decision, plan and child operation reference.
- A unique `(schedule_id, slot_key)` constraint is the HA/restart dedupe fence.
- A partial unique index permits only one `queued`, `running`, or `unknown` run
  per schedule. Reconciliation happens before new slots are evaluated.
- Child idempotency keys derive only from schedule ID and slot key, allowing the
  operation core to recover a submission after process interruption.

## Time semantics

- Cron is evaluated in the selected IANA timezone.
- `dstPolicy=first` selects the first occurrence of an ambiguous local minute;
  `second` selects the second; `skip` records suppression for both.
- A forward DST jump records matching nonexistent cron minutes as
  `dst_nonexistent`; it never shifts them to a different wall-clock time.
- Explicit holiday dates and recurring local blackout windows are evaluated in
  the same timezone as the cron expression.

## API and UI

- VM-scoped list/create/update/delete and run-history endpoints.
- Manual preview/run endpoint reuses the same preflight and durable dispatch
  path; execute still requires typed confirmation.
- The common VM details view exposes schedule authoring, status, last outcome,
  history and operation links to administrators, with read-only visibility for
  other host viewers.

## Acceptance evidence

- cron/timezone validation and stable-target enforcement;
- dry-run never calls a provider submit adapter;
- DST first/second/skip and forward-gap behavior;
- duplicate tick, restart and leader handover produce one due-slot record;
- blackout/holiday suppression and no emergency override;
- optimistic version conflict and execute typed confirmation;
- existing operation preflight/idempotency reused for all mutations;
- active-run lock, unknown outcome visibility and automatic disable threshold;
- API RBAC/host scope, audit, UI contract, lint and focused tests.
