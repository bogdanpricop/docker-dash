# V4.4k — VM NIC link control assumption audit

| Assumption | Evidence / decision | Result |
|---|---|---|
| Link-up capability implies detach is safe | Connect/disconnect and device removal have different failure and data-loss boundaries | Rejected; this workflow cannot detach/delete/remap |
| Any connected NIC except the last one is safe to disconnect | A non-last NIC may carry management, boot or application traffic | Rejected; require explicit short-lived evidence for all three dependencies |
| Client-supplied booleans are enough at submission | Browser state can be stale or tampered with | Rejected; store admin declaration server-side and re-read it in the worker |
| A safety declaration remains valid after VLAN/network changes | The dependency boundary changes when the attachment identity changes | Rejected; bind the declaration to a hardware/network fingerprint |
| An old declaration can be reused indefinitely | Guest and operational dependencies change over time | Rejected; bounded validity, four hours by default and at most 24 hours |
| Unknown current link state can be treated as disconnected | That can hide provider or guest telemetry loss | Rejected; current state must be a provider-reported boolean |
| A successful native task proves the desired state | Providers can complete a task before inventory converges or with partial effects | Rejected; mandatory post-read verification |
| Failed verification should trigger automatic inverse mutation | Provider outcome may be ambiguous and the inverse action can amplify an incident | Rejected; return `unknown` and a manual fresh-preflight rollback plan |
| One release flag is sufficient for all providers | Adapter confidence and canary evidence differ by provider | Rejected; independent default-off flags |
| Xen Orchestra/raw Xen can reuse XenAPI methods | Their management contracts and task semantics differ | Rejected; mutation is XenAPI-only until separately conformance tested |
