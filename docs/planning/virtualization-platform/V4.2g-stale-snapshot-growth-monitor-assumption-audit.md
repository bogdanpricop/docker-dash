# V4.2g — Stale snapshot growth monitor assumption audit

| Assumption | Failure mode | Required control |
|---|---|---|
| Snapshot age alone proves risk | long-lived intentional checkpoints become false criticals | configurable thresholds, evidence reasons and no automatic remediation |
| VM disk size approximates snapshot delta size | severe over/under-estimation | bytes remain unknown unless explicitly provider-reported |
| A missing parent means depth one | truncated/orphan graphs appear healthy | unknown depth plus integrity/coverage warning |
| Any VM with snapshots needs consolidation | healthy trees appear broken | only live `runtime.consolidationNeeded=true` is evidence |
| Daily size absence means zero growth | missing telemetry looks healthy | growth remains `null` with explicit size coverage |
| Every collection succeeds | one provider/VM blocks fleet monitoring | bounded per-VM errors and partial coverage |
| Polling on every page view is harmless | provider rate-limit and latency amplification | cached GET; explicit/admin refresh; six-hour leader-only job |
| Persistent critical state should alert every tick | notification fatigue | state/fingerprint transition dedupe |
| First scan should alert everything | noisy deployment baseline | first observation establishes state silently |
| Snapshot risk permits cleanup | unexpected data loss and consolidation load | no provider mutation path in service, route, job or UI |

## Pre-implementation checks

1. Extend the existing canonical snapshot store instead of adding native
   references to a second inventory.
2. Keep provider byte evidence optional end to end.
3. Bound host inventory, response items, history and observation JSON.
4. Verify cross-host scoping in service and route tests.
5. Verify alert transitions, recovery and unchanged-state dedupe.
6. Verify the browser-facing output never includes encrypted/native references.
