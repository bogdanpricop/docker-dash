# V2.5 — Affinity inventory and placement advisory feature spec

**Status:** implemented and repository-validated; deployment pending
**Release gate:** `DD_PROVIDER_PLACEMENT_ADVISORY=false` by default
**Backlog:** B069, B071–B072; B201/B203/B205 telemetry subset
**Scope:** read-only inventory, recommendation and rebalance dry-run; no migration or rule mutation

## Outcome

An authorized user can inspect portable affinity/anti-affinity evidence, request an explainable placement recommendation for one VM and generate a bounded fleet rebalance dry-run. Every target separates hard blockers, soft preferences, capacity/compatibility evidence, freshness and confidence. No recommendation executes a provider action.

## Contract

- affinity rule schema `1.0`: opaque rule/domain/VM/host IDs, kind, enabled, mandatory, compliance, members, source and limitations;
- telemetry schema `1.0`: canonical resource ID, CPU/memory observations, unit, provenance, observed time, freshness and collection limitations;
- recommendation schema `1.0`: source VM/host, candidate targets, 0–100 score, evidence coverage, confidence, dimensions, blockers, warnings, compatible migration modes and semantic plan hash;
- rebalance schema `1.0`: bounded proposed moves, source/target pressure before/after, estimated duration/downtime, skipped workloads, assumptions, expiry and semantic plan hash.

Unknown CPU, memory, storage, network, NUMA or policy evidence never becomes a pass. A high score with incomplete evidence is capped and labeled low/medium confidence.

## Provider matrix

| Provider plane | Affinity inventory | Native recommendation | Common advisory |
|---|---|---|---|
| Proxmox VE 9+ | HA node/resource affinity rules | none in the selected stable API | capacity + migration compatibility + rule evidence |
| Proxmox VE 8 | explicit unsupported rule inventory | none | capacity + migration compatibility; affinity stays unknown |
| vCenter | DRS VM–VM and VM–host rules/groups | read-only DRS recommendation evidence when exposed | native evidence plus common scoring |
| standalone ESXi | unsupported | unsupported | no alternate target in the endpoint boundary |
| Xen XAPI | VM home-server hint and VM-group anti-affinity | WLB recommendation details are not assumed available | pool capacity + migration compatibility + placement policies |
| Xen Orchestra | exposed home/group fields when available | no portable WLB contract assumed | bounded XO inventory evidence |
| raw Xen | unsupported | unsupported | no managed multi-host placement boundary |

## API and RBAC

- `GET /api/providers/:hostId/placement/affinity` — endpoint viewers;
- `GET /api/providers/:hostId/virtual-machines/:resourceId/placement/recommendations` — endpoint viewers;
- `POST /api/providers/:hostId/placement/rebalance/plan` — admins with endpoint operate access, audited as an expensive read-only plan.

All endpoints return 404 while the release gate is off. Provider failures are sanitized. Native object references and provider addresses are never returned.

## Safety and bounds

1. same-endpoint targets only;
2. maximum 64 target hosts, 500 inventory VMs and 20 rebalance candidates;
3. at most two concurrent per-VM recommendation reads;
4. no target can be proposed while offline, in maintenance, reserved for maintenance or blocked by a mandatory rule;
5. rebalance plans expire after five minutes and remain non-executable in V2.5;
6. the planner never claims CPU, NUMA, storage or network compatibility when the provider did not prove it;
7. native recommendation text is sanitized and treated as evidence, never authorization;
8. no `ApplyRecommendation`, migrate, affinity mutation or HA mutation call exists in this batch.

## Backlog mapping audit

The implementation plan lists B201–B225 both under V2.5 and V6.4. V2.5 implements the minimum placement telemetry foundation from B201, B203 and B205. Provider time-series adapters, charts, event ingestion/correlation, alerting, forecasting, AIOps, exports, SLOs and privacy administration (B202, B204, B206–B225) remain in V6.4, where the plan names their actual outcome. IDs are not renumbered and no feature is marked complete early.
