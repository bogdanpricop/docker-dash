# V3.1 — Recovery-point inventory deep specification

## Data flow

```text
PVE node/storage content OR XO public backup collections
  -> provider adapter (read-only projection + provider-local de-duplication)
  -> bounded common normalizer
  -> canonical workload lookup + encrypted native identity persistence
  -> filters and evidence coverage
  -> host-scoped API
  -> read-only Recovery Points page
```

The live provider response defines current inventory. Persistence supplies stable opaque identities and future restore correlation; V3.1 does not merge disappeared historical records back into the live response.

## Persistence model

Migration 117 adds two additive tables:

- `provider_backup_repositories`: canonical ID, endpoint/provider, native-reference hash and ciphertext, bounded public JSON, observation timestamps;
- `provider_recovery_points`: canonical ID, repository relation, endpoint/provider, archive and workload reference hashes/ciphertext, optional canonical workload ID, bounded public JSON and creation/observation timestamps.

The schema does not store repository URLs, credentials, encryption keys, backup payloads or provider sessions. Deletes cascade only from the endpoint. Repository deletion sets the recovery-point relation to null so a forward-compatible identity record cannot violate referential integrity during refresh.

## Identity and workload correlation

Repository identity is derived from endpoint plus provider-native repository reference. Recovery-point identity is derived from endpoint plus archive/volume reference. Both are stable across rename and opaque outside the server.

Workload correlation tries a provider UUID first, then bounded native aliases against existing encrypted common VM identities. Failure to map is not data loss: the point remains visible with `id: null` and `missingFromInventory: true`. V3.1 does not create a phantom VM identity from backup metadata.

## Proxmox adapter

1. Read cluster nodes.
2. Read each node's storage status without retrieving storage configuration or secret properties.
3. Register each shared store once; distinguish node-local stores with an internal `storage@node` identity.
4. Query only active, enabled, backup-capable storage with `content=backup`.
5. De-duplicate shared volumes by `volid`; keep local volumes scoped to their repository.
6. Infer guest type only from documented subtype/backup path markers and map `qemu/<vmid>` or `lxc/<vmid>` as workload aliases.
7. Treat PBS points as incremental-chain restore points and ordinary PVE files as full artifacts. This mode describes storage mechanics, not application consistency.
8. Continue on individual storage failure, report a bounded partial-inventory limitation, and fail the read when no node storage inventory is readable.

Repository-level PBS verification/encryption/protection support is capability metadata. A point is `verified`, `encrypted` or `protected` only when its content row supplies corresponding evidence.

## Xen Orchestra adapter

The probe reads `/rest/v0/docs/swagger.json`. `backup.read` is conditional only when GET operations for both `backup-repositories` and `backup-archives` are present. Inventory uses field projections and fixed limits:

- repository fields: `id,name,enabled`;
- archive fields: `id,backupRepository,jobId,mode,scheduleId,size,timestamp,vm,differencingVhds,dynamicVhds,withMemory`.

The repository URL field is deliberately absent. Only archives whose repository is present in the bounded repository collection are accepted. Archive presence does not imply health; V3.3 may correlate safe backup-log/health-check evidence.

Direct XAPI and raw Xen never fall back to snapshots or filesystem guessing. `backup.run` stays unsupported even when XO read inventory is available.

## Normalization rules

| Field | Rule |
|---|---|
| timestamps | valid ISO output; seconds converted when numeric values are below 10 billion |
| sizes | finite non-negative numbers only |
| text | control whitespace collapsed and hard length bounds |
| verification | strict synonym allowlist; anything else `unknown` |
| mode | only `full`, `incremental`, `delta`; otherwise `unknown` |
| consistency | only explicit `application`, `filesystem`, `crash`; otherwise `unknown` |
| booleans | true/false only; absent/coerced ambiguity becomes null |
| response | 2 MiB maximum after normalization and filtering |

Filters apply after persistence so a narrow response does not change what was observed. Sort order is descending creation time with canonical ID as a deterministic tie-breaker.

## Failure behavior

- invalid filters: typed 400 before provider inventory access;
- feature off: typed 404;
- unreachable provider: sanitized 502;
- unsupported provider/version: typed 400 with capability reason;
- malformed/oversized provider collection: sanitized 502;
- invalid normalized record or database failure: sanitized 500 and transaction rollback;
- partial PVE storage reads: successful envelope plus limitation;
- missing XO route: fail closed, never fall back to private/deprecated calls;
- unmatched workload/repository: visible unknown/null relationship rather than fabricated identity.
