# V2.3 — Host maintenance orchestration feature spec

**Status:** approved for implementation
**Release gate:** `DD_PROVIDER_HOST_MAINTENANCE=false` by default
**Depends on:** V2.1 migration compatibility and V2.2 durable `vm.migrate`

## Outcome

An administrator can preview and run a repeatable host drain with a bounded wave size, pause or resume it after a process restart, and obtain persistent evidence that no managed VM remains on the source host. Where the provider exposes a durable maintenance primitive, the same run can enter and later exit native maintenance mode.

## Scope

- read-only evacuation plan for one canonical host inside one provider endpoint;
- target selection from fresh V2.1 compatibility evidence, including aggregate memory reserve;
- `drain` and `enter` goals, exact-name confirmation, semantic plan hash and five-minute TTL;
- persistent run, per-VM item and event records;
- child `vm.migrate` operations dispatched in waves of 1–10;
- pause, resume, cancel-before-native-entry and exit controls;
- auto-pause on child `failed`, `cancelled` or `unknown` state;
- a local maintenance reservation that excludes the source host from new Docker Dash migration plans;
- final live inventory verification before `drained` or native `maintenance` is reported;
- native vSphere `EnterMaintenanceMode_Task` / `ExitMaintenanceMode_Task` support;
- native XAPI `Async.host.disable` / `Async.host.enable` support;
- Proxmox controlled drain with local reservation; native maintenance activation is reported unavailable instead of guessed;
- admin-only mutation routes, host-scope authorization and audit events;
- common Virtual Machines UI for plan review and run control.

## Anti-scope

- patch installation, reboot, firmware, vLCM or rolling cluster upgrades;
- HA admission-control mutation, affinity rules or placement-policy mutation;
- automatic cold power-off of running workloads;
- moving workloads back to their original host;
- cross-endpoint/cross-provider migration;
- raw `xl`/`xm` maintenance mutation;
- shell/SSH fallback for provider maintenance commands;
- Xen Orchestra maintenance mutation until a task-backed action is discovered and contract-tested.

## Backlog correction

The implementation plan associates V2.3 with B066–B070, but the market backlog defines host maintenance as B062–B065 and B066–B070 as HA/affinity. V2.3 follows its named outcome and implements B062–B065. IDs are not renumbered; HA and affinity remain in V2.4–V2.6.

## Provider matrix

| Provider plane | Drain | Native enter/exit | Evidence |
|---|---:|---:|---|
| Proxmox VE cluster | yes | no | controlled V2.2 migration plus local reservation |
| vCenter | yes | yes | durable HostSystem tasks and live host state |
| standalone ESXi | only when another target is visible (normally blocked) | yes | HostSystem tasks; evacuation remains caller responsibility |
| Xen XAPI pool | yes | yes | host disable/enable task and VM placement verification |
| Xen Orchestra | plan only when migration evidence exists | no | fail closed until a task-backed maintenance action is discovered |
| raw Xen | no | no | no managed multi-host task boundary |

## API

- `POST /api/providers/:hostId/host-maintenance/preflight`
- `POST /api/providers/:hostId/host-maintenance/runs`
- `GET /api/providers/:hostId/host-maintenance/runs`
- `GET /api/providers/:hostId/host-maintenance/runs/:runId`
- `POST /api/providers/:hostId/host-maintenance/runs/:runId/pause`
- `POST /api/providers/:hostId/host-maintenance/runs/:runId/resume`
- `POST /api/providers/:hostId/host-maintenance/runs/:runId/cancel`
- `POST /api/providers/:hostId/host-maintenance/runs/:runId/exit`
- `POST /api/providers/:hostId/host-maintenance/runs/:runId/reconcile`

Preflight input:

```json
{
  "sourceHostId": "ddr_host_…",
  "goal": "enter",
  "waveSize": 2,
  "nonMigratablePolicy": "block"
}
```

Submission additionally requires `planHash`, `confirm: true`, exact `confirmName`, and an `Idempotency-Key` header.

## State machine

```text
queued → preparing → draining → drained
                         │          │
                         │          └→ entering → maintenance → exiting → completed
                         ├→ paused ───────────────┘
                         ├→ failed
                         ├→ unknown
                         └→ cancelled
```

`drained` and `maintenance` are stable active states, not completed history: their reservation remains in force until `exit` succeeds. A run with deferred non-migratable workloads pauses and never claims that the host is empty.

## RBAC and audit

| Action | Viewer | Operator | Admin | Audit |
|---|---:|---:|---:|---|
| list/read | host view | host view | yes | no mutation |
| plan | no | no | yes | plan generation is audited |
| submit/pause/resume/cancel/exit | no | no | yes | actor, endpoint, host, run, goal, wave size and result |

No provider credential, native task reference, encrypted plan or idempotency value is returned to the browser or audit log.

## Safety and failure rules

1. A run cannot start when another active run reserves the same canonical source host.
2. A target reserved by any active maintenance run is a migration blocker.
3. Every child is re-preflighted immediately before submission.
4. A child in `unknown` pauses the run; no additional wave is launched.
5. Provider transport loss after a native task submission never causes automatic replay.
6. Native maintenance is entered only after live inventory reports zero VMs on the source host.
7. `exit` does not move VMs back and is separately audited.
8. Cancel stops new waves and requests cancellation only for currently cancelable child operations; uncertain outcomes remain visible.
