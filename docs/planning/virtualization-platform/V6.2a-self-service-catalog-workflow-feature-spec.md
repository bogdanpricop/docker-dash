# V6.2a — Infrastructure self-service catalog and request workflow

**Release:** v8.68.0

**Backlog:** B356–B365

**Date:** 2026-07-30

## Outcome

This batch provides a permission-filtered entry point from discovery to an
approved, durable provider operation. It does not introduce a second executor:
VM provisioning, power and snapshot fulfillment reuse the provider preflight,
idempotency, locking and reconciliation engine already used by administrators.

## Discovery and selection

- The global command palette searches catalog items, accessible projects and
  request IDs alongside existing resources. Unavailable actions carry a
  capability or configuration reason and remain navigation-only.
- The selection basket is persisted per user and accepts VM and container
  resources from separate pages. Its preview intersects safe actions and
  identifies mixed kinds or multiple endpoint blockers before bulk work.

## Catalog and forms

- VM, application and cluster offerings have an owner and explicit active,
  deprecated or retired item lifecycle.
- Versions retain a SHA-256 content identity, changelog, compatibility, dynamic
  form schema, fulfillment definition and cost model. Draft, published,
  deprecated and retired transitions are explicit; retired versions are
  immutable.
- Forms support bounded string, integer, boolean and enum fields, conditional
  visibility, required/range/pattern validation and estimated cost. Unknown,
  hidden or secret-shaped inputs fail closed.

## Requests and projects

- Project policies constrain offering slugs, lifecycle actions, maximum risk
  and whether approval is required.
- VM request preview shows validation, projected CPU/RAM/storage usage, hard
  quota blockers and estimated recurring cost.
- Approval requests bind the normalized payload, risk, diff, cost and expiry to
  the existing separation-of-duties engine. Approve and reject decisions retain
  comments.
- Ordered request events implement requested → approved → running → validated,
  with explicit rejected, expired and failed outcomes.
- The project dashboard combines assigned resources, quota posture, alerts,
  recent request counts and an honest FinOps attribution boundary.

## Fulfillment and safety boundaries

- Provider host, template, storage and node mappings live only in the private
  catalog version payload. Requesters receive provider type and configuration
  readiness, never fabric identifiers.
- Approved VM creation performs a fresh provider preflight before an approver
  submits the durable operation with plan hash, confirmation and idempotency.
- Project lifecycle requests accept only canonical assigned VM identities.
  Power and snapshot use the same approved durable path; console authorization
  is a policy-scoped, audited deep link and starts no mutation.
- Catalog and request payloads reject credential-shaped keys. Provider private
  configuration is excluded from API request/timeline responses and audit data.
