# V3.8 — DR objectives and provider security assurance

**Status:** implemented locally, provider mutations fail-closed

**Market features:** B149–B158

**Release gate:** `DD_PROVIDER_SECURITY_ASSURANCE=false`

## Outcome

This increment completes the planning/evidence boundary for non-disruptive DR
tests and introduces a versioned provider-security evidence control plane:

- protection-group dashboards expose workload-level RPO/RTO compliance and
  isolated-test readiness for bubble networks and temporary clones;
- versioned security packs normalize Secure Boot, vTPM, disk/saved-state/
  migration/backup encryption, confidential-compute and hardening evidence;
- a KMS/key-provider registry tracks bounded health, certificate expiry and
  canonical affected resources while returning no credential reference;
- confidential-VM compatibility preflights bind trusted-image, target-host and
  healthy key-provider evidence to an expiring deterministic plan.

The implementation accepts provider-reported or explicitly imported metadata.
It does not scan an endpoint, contact a KMS, run a host command, create a clone
or provision a VM. Missing evidence is `unknown`, never compliant.

## DR test and objective contracts

The existing V3.6 test runbook already compiles a bubble network, source
isolation boundary, temporary per-member restore clones, validation and
ownership-marked cleanup. The overview now publishes, for every protection
group:

- test readiness and its concrete blockers;
- isolated mapping count and temporary clone count;
- workload counts for RPO and RTO `met`, `breached` and `unknown`;
- explicit `executorReleased:false` while provider test mutation is absent.

RPO uses verified recovery-point or replication evidence. RTO uses successful
automated restore-drill duration. Rehearsal evidence cannot impersonate a real
failover and the dashboard preserves unknown values.

## Versioned security evidence

`provider_security_evidence` scopes one current pack observation to a canonical
endpoint, host, VM or artifact. Facts are closed-schema and bounded. Pack keys
and versions are selected by provider type; PVE, vSphere, Xen, Hyper-V,
Nutanix and KubeVirt definitions are published even where no collection adapter
exists. Capability declarations stay explicitly unsupported until a
conformance-tested collector exists.

The assessment derives controls only from supplied facts:

| Domain | Normalized evidence |
|---|---|
| Secure Boot | capable, enabled, compliant, firmware |
| vTPM | presence, version, state, migration and clone constraints |
| Encryption | disk coverage plus saved-state, migration and backup state |
| Confidential VM | current mode, supported/compatible modes and constraints |
| Hardening | versioned baseline key and pass/fail/unknown checks |

No omitted domain receives a pass.

## KMS and confidential provisioning

`provider_key_providers` stores a credential-free HTTPS origin and a symbolic
secret-manager URI. Public responses replace the secret reference with a
SHA-256 digest. Inline credentials, URL user-info and out-of-scope affected
resources are rejected. Health and certificate data are reported evidence;
the registry performs zero network calls.

`provider_confidential_provisioning_plans` checks fresh artifact/host evidence,
requested SEV/SEV-ES/SEV-SNP/TDX/shielded mode, Secure Boot, vTPM, encrypted
storage/migration and a healthy non-expiring key provider. Every plan expires
after five minutes and returns `executionAuthorized:false`; actual VM creation
remains a separate guarded provisioning workflow.

## Security, RBAC and audit

- endpoint viewers may read assurance and key-provider posture;
- only admins with endpoint operate permission and write mode may import
  evidence, manage registry entries or persist a compatibility preflight;
- canonical resource scope is checked server-side;
- UI escapes names, IDs, findings, origins and evidence hashes;
- audit events record hashes and safety boundaries, never secret references;
- key-provider deletion is soft and never touches an external provider.

## Verification

- migration constraints and foreign keys;
- closed fact schema, scope, timestamp, count and size limits;
- absence-is-unknown and control derivation tests;
- symbolic-secret and credential-free HTTPS validation;
- confidential compatibility, staleness and no-execution assertions;
- DR workload objective and isolated-test readiness aggregates;
- admin/host-scope/API audit tests and UI escaping;
- full Jest, ESLint, i18n, accessibility and feature-registry gates before tag.
