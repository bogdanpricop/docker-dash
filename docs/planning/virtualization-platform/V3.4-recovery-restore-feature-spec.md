# V3.4 — Recovery restore feature specification

**Status:** implemented, validated, and deployed to staging; provider-real canary pending

**Release gate:** `DD_PROVIDER_RECOVERY_RESTORE=false` by default

**Mutation scope:** create-only full VM/CT restore through Proxmox VE

**Safety boundary:** restore never overwrites, starts, live-restores, deletes, or reconnects a workload automatically

## Outcome

V3.4 turns a canonical V3.1 recovery point into a short-lived, deterministic restore plan and, when every gate passes, one durable `vm.restore` operation. The first executable provider slice is Proxmox VE because its API exposes a task-backed create/restore boundary for QEMU and LXC archives. Xen Orchestra, XAPI, raw Xen, vSphere, ESXi, disk-level restore, file-level restore, differential restore, and instant/live restore remain explicit fail-closed capability states until a conformance-tested mutation or streaming contract exists.

The restore target is always a new VMID on an explicitly selected PVE node and storage. Docker Dash submits `force=false`, `start=false`, and unique network identities. A provider error or cancellation can leave partial provider resources, so Docker Dash records the outcome and requires inspection; it never guesses that deleting the target is safe.

## User stories

1. An administrator can select a recovery point and see live target-node, target-storage, capacity, verification, conflict, and capability evidence without mutation.
2. A verified recovery point can be restored only after exact target confirmation and an idempotency key.
3. An unknown, stale, or unverified point requires an explicit override reason and stronger typed confirmation; a failed point cannot be overridden.
4. A target VMID that already exists, is reserved by another active restore, or becomes occupied after planning fails closed.
5. A process interruption around provider submission never replays the restore; Docker Dash reconciles the target and native task or ends `unknown`.
6. A viewer can follow the durable operation through Activity Center without seeing archive volume IDs, storage native IDs, provider task IDs, or credentials.
7. Cancellation requests the native PVE task stop when possible and reports that manual cleanup may be required.

## API

| Method | Path | Access | Effect |
|---|---|---|---|
| `POST` | `/api/providers/:hostId/recovery-points/:pointId/restore/preflight` | admin + host operate | generate a live, non-mutating restore plan |
| `POST` | `/api/providers/:hostId/recovery-points/:pointId/restore` | admin + host operate + global writeable | enqueue one idempotent durable restore |

The submit route requires `Idempotency-Key`, the current `planHash`, `confirm=true`, and exact `confirmText`. General `/api/operations` routes own progress, events, cancellation, and manual resolution of `unknown` results.

## Supported request

```json
{
  "kind": "vm",
  "targetNodeId": "ddr_host_<opaque>",
  "targetStorageId": "ddr_storage_<opaque>",
  "targetVmid": 9123,
  "allowUnverified": false,
  "overrideReason": null
}
```

Only `kind=vm` can become executable in this batch. `file` and `disk` produce stable blocker codes instead of silently falling back to a full restore.

## Acceptance criteria

- a separate release flag defaults off and is visible in preflight evidence;
- the capability catalog distinguishes VM, disk, file, instant, and differential restore;
- recovery-point, node, storage, archive, and native task references remain encrypted/server-side;
- plan hashing excludes volatile timestamps but includes verification, override, target, capacity, conflict, capability, and provider evidence;
- submit recomputes the live plan and rejects a stale hash;
- failed verification, inaccessible source, missing target content type, insufficient known capacity, existing VMID, and active reservation are blockers;
- full PVE QEMU/LXC restore uses a new VMID, `force=false`, `unique=true`, and `start=false`;
- the non-idempotent provider call has a pre-submit checkpoint and is never replayed after ambiguity;
- native UPID progress/cancellation and post-restore live inventory are reconciled durably;
- success requires a new target with the requested type/node/VMID and stopped state;
- provider failure/cancel never triggers automatic target deletion;
- routes sanitize upstream errors and audit only canonical IDs and bounded intent;
- service, handler, client, catalog, route, UI, full-suite, lint, staging, database, HTTP, and container checks pass.
