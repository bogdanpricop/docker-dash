# V2.2 — Native VM migration deep spec

## State and trust boundaries

`provider-operations/vm-migration` builds the public execution plan from the V2.1 compatibility envelope. Only canonical IDs cross the API boundary. The operation request stores target/mode/storage canonical IDs and the semantic plan hash encrypted at rest. Native VM, host, datastore, and task references are resolved or produced server-side.

The operation handler is non-idempotent with retry policy `none`. It submits at most once, persists the returned native task reference, and then reconciles. If a provider response is ambiguous, reconciliation checks observed placement; it must never replay migration merely because no task reference was captured.

## Plan contract

The semantic hash covers provider endpoint, VM identity/name/power state, source target, selected target, mode, optional target storage, selected mode blockers/warnings/estimate, release/policy/conflict gates, and validity bucket. Volatile timestamps and display-only checks are excluded.

Every migration requires `confirm=true` and the exact VM display name. Plans expire on a five-minute boundary. Cold mode requires a stopped VM. Live mode requires a running VM. Storage mode follows provider evidence and never implies cross-endpoint movement.

## Provider bridges

- Proxmox VE: POST the QEMU/LXC `migrate` endpoint and require an UPID. QEMU can use online and local-disk transfer options; LXC live migration remains blocked. Task state uses the existing node task API and DELETE cancellation.
- vSphere: call `RelocateVM_Task` with the selected `HostSystem`; storage mode additionally requires a resolved `Datastore`. Task state and `info.cancelable` are read from the Task object; cancellation calls `CancelTask` only when advertised.
- XAPI: call `Async.VM.pool_migrate(vm, host, options)` with explicit `live`; task progress/state uses the task record and cancellation uses `task.cancel`.
- Xen Orchestra: discover the action and required field names from the endpoint OpenAPI schema. Unknown schemas are unsupported, not guessed.
- Raw Xen: unsupported because the adapter cannot provide durable task reconciliation.

## Recovery algorithm

1. Resolve endpoint and canonical VM/target identities.
2. Read current VM placement and power state.
3. If already on target, finish as verified (covers acknowledged-but-response-lost submission).
4. If no native task was persisted and placement is still source after an attempted execute, return `unknown`; never submit again.
5. If a task exists, poll until pending/success/failure.
6. On task success, poll inventory until the VM is observed on target and its power state satisfies the mode expectation.
7. If verification times out, mark `unknown` with bounded sanitized evidence.

## Security and operations

- Feature flag: `DD_PROVIDER_VM_MIGRATION`, default false.
- Roles: admin/operator plus host `operate`; global read-only middleware applies to submission.
- Lock scopes: VM, target host, and selected storage.
- No credential/native-ref response fields; audit records canonical IDs and operation ID.
- Timeout: 24 hours; cancellation remains provider-specific and best effort.
