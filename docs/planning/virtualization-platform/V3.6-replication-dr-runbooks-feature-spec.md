# V3.6 — Replication and DR runbooks feature specification

**Status:** implemented; rollout validation pending

**Release gate:** `DD_PROVIDER_DR_RUNBOOKS=false` by default

**Executable scope:** read-only replication inventory, durable protection-group definitions, deterministic failover/failback/test plans, non-mutating rehearsals, and measured RPO/RTO compliance

## Outcome

V3.6 turns recovery evidence into an application-level disaster-recovery plan. Administrators define a protection group, workload dependencies, recovery placement and network mappings, then compile a deterministic runbook for planned failover, unplanned failover, failback, or isolated test. A rehearsal evaluates the entire plan without changing a provider and stores tamper-evident evidence.

Provider mutation remains fail-closed until the endpoint exposes a conformance-tested native recovery-plan transport. Proxmox storage replication is reported as intra-cluster asynchronous replication and is never mislabeled as cross-site DR. Standard vSphere credentials do not imply VMware Live Recovery/SRM access. Xen Orchestra archive or continuous-replication evidence does not imply a public task-backed failover action.

## User stories

1. An administrator can create a bounded protection group from canonical VMs and define dependency/boot stages without provider-native identifiers.
2. Target host, cluster, storage and network mappings are canonical and scoped to the configured recovery endpoint.
3. The service rejects duplicate members, unknown identities, dependency cycles, future-stage dependencies and unbounded mappings.
4. A read-only Proxmox inventory shows configured storage-replication jobs, schedules, target nodes and enabled state without exposing job/native identities.
5. Planned failover, unplanned failover, failback and isolated-test previews show ordered steps, blockers, warnings, blast radius and exact authorization requirements.
6. A rehearsal never submits a provider task. It records the current replication, recovery-point, restore-drill, dependency and mapping evidence under a semantic SHA-256 hash.
7. The compliance dashboard distinguishes `met`, `breached`, `failed`, `unknown` and `never_tested`; operator-attested or plan-only evidence never masquerades as an automated DR test.
8. Real failover/failback/test submission is rejected with a typed capability error until a provider adapter owns the complete isolate/promote/validate/reprotect lifecycle.

## API

| Method | Path | Access | Effect |
|---|---|---|---|
| `GET` | `/api/providers/:hostId/dr/overview` | host view | groups, compliance and recent rehearsal evidence |
| `GET` | `/api/providers/:hostId/dr/replications` | host view | read-only provider replication inventory |
| `GET` | `/api/providers/:hostId/dr/protection-groups` | host view | protection groups |
| `POST` | `/api/providers/:hostId/dr/protection-groups` | admin + host operate | create a protection group |
| `PUT` | `/api/providers/:hostId/dr/protection-groups/:groupId` | admin + host operate | replace desired protection-group state |
| `DELETE` | `/api/providers/:hostId/dr/protection-groups/:groupId` | admin + host operate | soft-delete a group without deleting evidence |
| `POST` | `/api/providers/:hostId/dr/protection-groups/:groupId/preflight` | admin + host operate | compile one runbook mode without mutation |
| `POST` | `/api/providers/:hostId/dr/protection-groups/:groupId/rehearse` | admin + host operate | persist a non-mutating evidence rehearsal |
| `GET` | `/api/providers/:hostId/dr/runs` | host view | bounded rehearsal history |

## Release guarantees

- all group and run identifiers are opaque and server-generated;
- native provider references remain encrypted in the existing identity stores;
- every graph and mapping is size-bounded and validated before persistence;
- group enablement requires exact `AUTHORIZE DR <group name>` confirmation;
- real recovery modes require four-eyes authorization and a conformance-tested provider capability;
- a rehearsal has no provider mutation path and cannot be upgraded in place into a failover;
- RPO uses the newest verified recovery point for every member; RTO uses measured successful restore-drill evidence, never an estimate;
- a missing member signal makes compliance `unknown` or `never_tested`, not compliant;
- plan hashes exclude continuously changing age/presentation fields, bind stable recovery timestamps and include every threshold verdict and decision input.

## Out of scope for this execution slice

- automatic network/VLAN creation or DNS/IPAM cutover before the V4 fabric contracts;
- VMware Live Recovery/SRM mutation through ordinary vCenter credentials;
- cross-endpoint secret delegation;
- raw shell/PowerShell runbook steps;
- declaring an application recovered from manual acknowledgement alone;
- automatic production failover, failback, reprotect or destructive cleanup.
