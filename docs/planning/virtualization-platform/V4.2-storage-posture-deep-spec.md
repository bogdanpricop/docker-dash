# V4.2a — Storage posture deep specification

## Data flow

`GET /api/providers/:hostId/storage-posture` resolves an active authorized host, probes the existing Provider SDK envelope, checks `storage.health.read`, then reads the canonical `storage` inventory through `resourcesForHost`. The inventory path continues to normalize resources, persist the bounded snapshot and retain native identifiers only in the identity store. `storage-posture.js` projects public fields into posture signals; it has no provider mutation transport.

## Signal semantics

| Signal | Pass | Warning | Fail | Unknown |
|---|---|---|---|---|
| accessibility | provider explicitly reports true | — | provider explicitly reports false | field absent |
| maintenance | normalized `normal` | normalized maintenance | — | field absent/unrecognized |
| capacity | used <85% | used 85–<95% | used >=95% | capacity or used absent |
| overcommit | virtual allocation <= physical capacity | virtual allocation > capacity | — | either value absent/zero capacity |
| QoS | never inferred in V4.2a | — | — | adapter lacks a native conformance-tested source |
| multipath | never inferred in V4.2a | — | — | adapter lacks a native conformance-tested source |

Storage state is the highest observed severity: `fail`, then `warning`, then `pass`, otherwise `unknown`. QoS/multipath unknown signals do not downgrade a storage with otherwise passing observable health to unknown; they remain visible as missing coverage. This lets an operator distinguish capacity/access posture from unavailable diagnostics.

## Provider mappings

- Proxmox storage rows provide `maxdisk`/`disk` capacity information and `active`/status evidence. The adapter maps only explicit active/inactive/status values; omitted values become `null`, not false.
- vSphere reads `summary.capacity`, `summary.freeSpace`, `summary.accessible`, `summary.maintenanceMode` and `summary.type` through the PropertyCollector. Normalization derives used bytes from capacity minus free bytes.
- XenAPI/Xen Orchestra SR inventory provides physical size/usage, virtual allocation where supplied, type and shared/attached evidence. XO fields remain best-effort; raw Xen must advertise its storage inventory before posture is exposed.

## Security and bounds

- input is only the route host ID; host authorization is checked before provider contact;
- storage list limit is fixed to the SDK's maximum bounded inventory size (500);
- responses contain canonical storage IDs and sanitized display/capacity data, never provider native references, endpoint credentials or URLs;
- provider failures are converted to bounded route errors; unreachable providers return 502;
- no persistence beyond existing canonical resource snapshots is introduced.
