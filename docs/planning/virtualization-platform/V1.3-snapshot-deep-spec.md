# V1.3 Deep spec — Common VM snapshots

## API

- `GET /api/providers/:hostId/virtual-machines/:vmId/snapshots`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshots/preflight`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshots`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshots/:snapshotId/revert/preflight`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshots/:snapshotId/revert`
- `POST /api/providers/:hostId/virtual-machines/:vmId/snapshots/:snapshotId/delete/preflight`
- `DELETE /api/providers/:hostId/virtual-machines/:vmId/snapshots/:snapshotId`

Mutations require admin/operator, effective host `operate`, writeable mode, `Idempotency-Key`, live `planHash` and confirmation. Create uses `{name, description?, consistency}`. Revert uses typed VM name; delete uses typed snapshot name.

## Persistent identity/cache

Migration 110 adds `provider_vm_snapshots`. Canonical IDs are deterministic from host, VM and stable provider UUID when available, otherwise from the native ref; native refs are AES-256-GCM encrypted and matched by SHA-256. A refresh marks the VM inventory absent, then upserts every observed snapshot as present in one transaction. Rows remain as tombstones after provider deletion so operation history keeps a stable public ID.

Public metadata is bounded; provider payloads are never persisted. Parent links are resolved only to canonical IDs from the same refresh. Integrity states are `valid`, `orphan_parent`, `cycle`, or `unknown`.

## Provider mapping

| Common | Proxmox VE | vSphere/ESXi | Xen |
|---|---|---|---|
| list | `/snapshot` | VM `snapshot.rootSnapshotList/currentSnapshot` | XO/XAPI snapshot VM records |
| create crash | POST `/snapshot` | `CreateSnapshot_Task(memory=false,quiesce=false)` | `Async.VM.snapshot` / XO snapshot action |
| create quiesced | unsupported initially | `CreateSnapshot_Task(...,quiesce=true)` | `Async.VM.snapshot_with_quiesce` when advertised |
| revert | `/snapshot/{name}/rollback` | `RevertToSnapshot_Task` | `Async.VM.revert` / XO revert action |
| delete | DELETE `/snapshot/{name}` | `RemoveSnapshot_Task(removeChildren=false,consolidate=true)` | `Async.VM.destroy` / XO delete |

PVE and vSphere mutation responses return native tasks. XAPI uses task refs. XO responses are task-polled only when they expose a task ID; otherwise the handler enters post-verification.

## Preflight

Every plan binds host, VM, snapshot/action, current inventory graph, provider capability, requested consistency, VM power/tools evidence, policy, permission, conflicts, maximum count/depth and destructive confirmation. `validUntil` is five minutes and participates in the semantic SHA-256 plan hash.

All responses contain `protection` evidence stating `isBackup=false`, `failureDomain=provider_storage`, and a warning that deletion/storage loss can remove both VM and snapshot.

## Failure/reconciliation model

- confirmed provider rejection before task: failed;
- interrupted response after possible submit: reconciliation, never execute retry;
- task pending: durable reconciling with progress;
- task failure: failed with bounded sanitized error;
- create: refresh and require exactly one snapshot with the requested portable name;
- delete: refresh and require snapshot absent;
- revert: require task success (when available), VM present and target snapshot still present;
- unverifiable completion after timeout: `unknown`, VM lock retained;
- cancellation is confirmed only when the provider exposes and acknowledges native task cancellation.
