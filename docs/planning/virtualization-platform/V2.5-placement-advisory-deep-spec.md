# V2.5 — Placement advisory deep specification

## Data flow

```text
provider rules + common VM/host inventory + migration preflight + HA snapshot
  -> native-to-canonical relation resolver
  -> bounded telemetry normalizer
  -> policy evaluator + target scoring
  -> per-VM recommendation or greedy rebalance dry-run
  -> RBAC-scoped API and Placement Advisor UI
```

The service caches affinity inventory for 60 seconds and deduplicates concurrent reads. It persists no recommendation or native rule reference. Existing encrypted identity rows are the only native-reference boundary.

## Rule model

Kinds are `vm_vm_affinity`, `vm_vm_anti_affinity`, `vm_host_affinity`, `vm_host_anti_affinity` and `home_host_preference`. A rule contains opaque IDs only. Mandatory vSphere rules are hard blockers. Optional vSphere rules, Xen anti-affinity groups/home-server hints and non-strict Proxmox rules are preferences. Disabled rules remain visible but do not affect scoring.

For a target host:

- mandatory VM–host affinity blocks a target outside the allowed set;
- mandatory VM–host anti-affinity blocks a target inside the denied set;
- mandatory VM–VM anti-affinity blocks co-location with another running member;
- mandatory VM–VM affinity blocks separation from running members when their placement is known;
- equivalent optional rules subtract policy score and create warnings;
- incomplete member placement produces `unknown`, not compliance.

## Telemetry model

Only bounded scalar observations are accepted. CPU utilization is percent, memory and storage are bytes, and timestamps are ISO-8601. Provenance is `provider_inventory`, `provider_native` or `derived`. Freshness states are `fresh` (≤60s), `stale` (≤5m), `expired` (>5m) and `unknown`. Labels are fixed canonical IDs/provider/dimension; no native name or unbounded label enters the metric contract.

This is a placement snapshot, not the V6.4 time-series/event platform.

## Candidate dimensions and weights

| Dimension | Weight | Evidence |
|---|---:|---|
| hard feasibility | gate | availability, maintenance, reservation and ready migration mode |
| memory headroom | 30 | projected used bytes including VM configured memory and 10% reserve |
| CPU headroom | 20 | current provider CPU utilization; no fabricated workload projection |
| affinity policy | 20 | mandatory/optional normalized rules |
| migration compatibility | 15 | storage/network/device/CPU checks from V2.1 |
| HA posture | 10 | latest V2.4 state, endpoint-level caveat only |
| balance benefit | 5 | source pressure minus projected target pressure |

Only applicable dimensions enter the weighted average. The final score is capped by evidence coverage (`50 + coverage/2`). Confidence is high at ≥80% coverage, medium at ≥50%, otherwise low. Hard blockers always make the candidate ineligible regardless of score.

## Rebalance dry-run

1. Read at most 64 hosts and 500 VMs.
2. Identify source hosts whose known memory or CPU utilization is at least the requested threshold (default 85%, bounds 70–95%).
3. Consider at most 20 running VMs, largest configured memory first.
4. Request per-VM advisory evidence with concurrency two.
5. Select the highest eligible target that remains below the target ceiling after prior planned reservations.
6. Stop planning from a source when its projected known pressure falls below the target threshold (default 75%).
7. Return moves and skipped reasons, never execute them.

The plan hash excludes timestamps and includes VM/source/target IDs, selected mode, scores, projected pressure and policy evidence. The plan expires after five minutes and V2.6 must recompute it before any apply.

## Provider normalization

### Proxmox

`GET /cluster/ha/rules` is optional and version-gated to PVE 9+. Node-affinity rules map to VM–host relations; resource-affinity rules map to VM–VM affinity or anti-affinity. Unknown future rule types remain visible as limitations but do not affect scoring. PVE 8 returns unsupported affinity evidence without failing common capacity recommendations.

### vSphere

PropertyCollector reads `configurationEx.rule`, `configurationEx.group` and `drsRecommendation` from `ClusterComputeResource`. VM/host group names are resolved inside the same cluster. Mandatory, enabled, status and rule UUID/key are retained; native keys remain server-side. Standalone ESXi never calls cluster placement properties.

### Xen

XAPI reads `VM.affinity`, `VM.groups` and `VM_group.get_all_records`. Home-server affinity is a soft hint. `anti-affinity` VM groups are advisory because XenServer can breach them to complete operations, and WLB/home-server precedence is surfaced as a limitation. XO uses only fields its bounded REST projections expose. Raw Xen is unsupported.

## Failure behavior

- missing optional affinity APIs: typed unsupported/unknown envelope, common recommendation may continue;
- base VM/host inventory failure: sanitized 502;
- one VM recommendation failure in rebalance: skipped item, remaining items continue;
- incomplete relation mapping: unknown policy evidence;
- response over 1 MiB: fail closed;
- concurrent identical affinity read: one provider request;
- feature disabled: 404 for all three endpoints.
