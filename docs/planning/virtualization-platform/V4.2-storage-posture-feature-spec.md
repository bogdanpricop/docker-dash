# V4.2a — Storage posture feature specification

**Status:** shipped in v8.23.0 (2026-07-28)

**Release gate:** read-only; requires the existing `DD_PROVIDER_SDK_V2=true` contract. No storage mutation is enabled by this release.

## Outcome

The new **Storage Posture** page turns the canonical storage inventory into a bounded, provider-neutral assessment. It presents live provider evidence for accessibility, maintenance state, capacity and thin/virtual allocation where available. It also exposes whether policy, QoS and multipath evidence is actually available for the active endpoint.

An absent metric is never treated as a pass. In particular, QoS, multipath, Ceph, Longhorn, vSAN, S2D and appliance-specific telemetry remain `unknown` until an adapter implements and conformance-tests their native source.

## User stories

1. An operator with host `view` access can inspect a single endpoint's storage posture without receiving provider-native identifiers or credentials.
2. Each storage target shows capacity, used/free bytes, virtual allocation when supplied, type/content evidence and shared/local evidence.
3. Accessibility false and capacity at or above 95% are failures; maintenance mode, capacity from 85% through 94.9%, and virtual allocation above physical capacity are warnings.
4. A missing capacity, QoS, multipath or maintenance observation is presented as `unknown`, with an explanation.
5. The page makes no reservation, storage policy change, path probe, write test, snapshot consolidation or cleanup action.

## API

| Method | Path | Access | Effect |
|---|---|---|---|
| `GET` | `/api/providers/:hostId/storage-posture` | host view | fresh normalized storage inventory plus read-only posture assessment |

The response uses schema version `1.0`, provider endpoint identity, `observedAt`, capability evidence, a summary and bounded per-storage signals. Native provider references remain in the encrypted server-side identity store.

## Capability matrix

| Capability | Proxmox VE | vSphere / ESXi | XenAPI / Xen Orchestra |
|---|---|---|---|
| `storage.health.read` | cluster storage accessibility/capacity | datastore PropertyCollector accessibility, maintenance and capacity | SR attachment/capacity where the active management plane provides it |
| `storage.policy.read` | type, content classes and shared evidence | datastore type/capacity evidence | SR type/shared evidence |
| `storage.qos.read` | unsupported | unsupported | unsupported |
| `storage.multipath.read` | unsupported | unsupported | unsupported |

## Backlog coverage and deferrals

- This is the evidence foundation for B091–B100 and makes the existing B085–B086 capacity signals operator-visible.
- B091 snapshot consolidation remains deferred until a dedicated native task, preflight and rollback/partial-state contract is released.
- B092 QoS editor and B093 tiering recommendation remain deferred; this release does not pretend that inventory fields are enforcement or a recommendation.
- B094 shared-disk topology, B095 object registry, B096 NFS/SMB safe repository probes, B097 Ceph, B098 Longhorn, B099 appliance suites and B100 storage change plans remain explicit follow-on work.

## Guarantees and limits

- no provider write, test write, shell fallback or destructive operation is attempted;
- capability evidence is complete and fail-closed for every published storage key;
- `unknown` is distinct from `pass` in API and UI;
- observed capacity is point-in-time only and never replaces execution-time capacity validation;
- threshold results are advisory posture evidence, not an SLA or reservation;
- access remains scoped through `requireHostAccess('view')`.
