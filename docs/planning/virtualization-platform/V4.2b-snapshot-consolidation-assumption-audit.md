# V4.2b — Snapshot consolidation assumption audit

| Assumption | Counterexample | Contract decision |
|---|---|---|
| deleting a snapshot always consolidates all redo logs | deletion can fail or leave a consolidation-needed state | expose a separate native consolidation action |
| task success means disks are healthy | task completion can precede runtime state visibility | require post-read `runtime.consolidationNeeded=false` |
| a VM with snapshots needs consolidation | healthy snapshot trees normally do not | require explicit live runtime evidence |
| all providers expose an equivalent operation | Proxmox/Xen have distinct semantics and no portable task contract here | vSphere-only; others fail closed |
| consolidation is harmless maintenance | it can create sustained storage I/O | separate flag, admin role, typed VM confirmation and warning |
| retried mutation is safe | provider timeout can leave an accepted task | operation is non-idempotent with no automatic replay |

## Audit probes

1. Reject when the feature gate is off, the endpoint is not vSphere, or the capability is unknown/unsupported.
2. Reject when `consolidationNeeded` is false or absent before preview and again at worker execution.
3. Prove a wrong typed VM name or stale plan hash cannot queue a task.
4. Prove only `ConsolidateVMDisks_Task` is sent and native VM references remain server-side.
5. Prove task success stays reconciling until the runtime flag clears, then becomes unknown at the bounded deadline.
