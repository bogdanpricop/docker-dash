# V4.6c — Governance lifecycle and VM metrics foundation

**Release:** v8.52.0
**Backlog:** B196–B205
**Migration:** `126_governance_metrics_foundation.js`

## Outcome

V4.6c closes the remaining lifecycle controls in the governance wave and adds
the bounded telemetry contract needed by later observability batches. The
release is additive: it does not delete provider resources, start a background
collector, or infer missing provider counters as zero.

## Governance lifecycle

- Resource lease policies define maximum TTL, who may renew, a renewal ceiling,
  and the user accountable for cleanup. Expiry moves the control-plane record
  to `cleanup_pending`; cleanup must be attested explicitly.
- Production ownership policies can require an active owner, service and cost
  center. Project resource assignment fails with `OWNERSHIP_INCOMPLETE` when an
  enabled production policy is not satisfied.
- Separation-of-duties rules compare effective direct and team role bindings.
  A conflict is reported when the two scopes overlap through ancestry.
- Access review campaigns snapshot role/team bindings and active service
  accounts. A revoke decision expires a role binding or revokes a service
  token while preserving review evidence.
- Tenant exports use a documented JSON envelope, SHA-256 checksum, 10 MiB
  inline limit and seven-day validity. Token hashes and user password hashes
  are excluded.
- Controlled offboarding rejects the default tenant and requires suspension, a
  current export, no active lease/review, complete ownership, the exact
  `DELETE <slug>` phrase and checksum confirmation. Provider resources are not
  deleted by this workflow.

## VM metrics foundation

The canonical schema contains 13 bounded series across CPU, memory, disk,
network and uptime. Every stored sample includes its unit, sample time,
adapter, provider, resource key, labels, series fingerprint and provenance.

Adapters normalize payloads from:

- Proxmox VE RRD/API;
- XAPI or Xen Orchestra RRD;
- vSphere PerformanceManager or quickStats;
- Prometheus query/remote ingestion;
- Azure Monitor metric responses.

Adapters report partial coverage naturally: an absent native counter creates
no canonical sample. The integration does not claim live collection unless a
caller supplies observations through the authenticated ingestion API.

Freshness state is kept per provider host and VM resource with last sample,
lag, last error and consecutive error count. Polling decisions combine recent
activity, page visibility and a per-provider request budget. Cardinality policy
bounds resources, metrics, labels, label length and series per batch; rejected
samples are counted with bounded evidence and exported to Prometheus.

## API and UI

The authenticated admin API is mounted under `/api/governance/lifecycle`.
Identity & Policy Governance adds `Lifecycle` and `VM metrics` tabs for lease,
ownership, SoD, recertification, export/offboarding, freshness and policy
administration. All mutations remain subject to read-only mode, global
approval policies, blackout windows and audit logging.

## Safety invariants

1. Lease expiry never triggers provider deletion.
2. Unknown or missing metrics never become zero.
3. Metric labels and batch size are bounded before persistence.
4. Access-review revocation preserves the review item and original binding.
5. Tenant deletion is transactional and cannot target the default tenant.
6. Export/checksum and typed confirmation are both required at deletion time.
7. Provider credentials, service-token hashes and password hashes are not
   included in tenant exports.

## Verification

Dedicated in-memory SQLite tests cover the migration, TTL and renewal rights,
cleanup accountability, production ownership enforcement, direct/team SoD,
access-review revocation, export/offboarding gates, all five adapters,
freshness/errors, adaptive polling, cardinality rejection, Prometheus export
and UI/API wiring.
