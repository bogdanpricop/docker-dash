# V2.4 — HA readiness deep specification

## Data flow

```text
provider read-only APIs
  -> provider-specific bounded collector
  -> common evidence normalizer
  -> readiness scorer + conservative failure simulator
  -> encrypted, bucketed SQLite snapshot
  -> RBAC-scoped API
  -> High Availability dashboard/history
```

## Persistence

`provider_ha_snapshots` stores endpoint ID, provider type, observation time, five-minute bucket, state, score, semantic SHA-256 and encrypted canonical JSON. A unique `(host_id, observed_bucket)` constraint prevents scheduler/UI duplication. The latest 96 snapshots per endpoint are retained.

No credential, provider URL, native object reference or unbounded provider response is stored. The encrypted payload is capped at 512 KiB before insert.

## Signal model

Each signal has `key`, `state`, `reason`, `source` and `confidence`. Allowed states are `pass`, `warning`, `fail`, `unknown`, `not_applicable`. Essential signals are HA enablement, quorum/coordination, heartbeat/host monitoring, fencing/isolation, storage reachability and failover capacity.

Scoring includes only applicable signals. `pass` earns full weight, `warning` half, and `fail`/`unknown` zero. A score is explanatory, not a mutation threshold. Overall state precedence is:

1. unsupported capability → `unsupported`;
2. HA explicitly disabled → `not_configured`;
3. essential hard failure → `blocked`;
4. other failure/warning → `degraded`;
5. essential unknown → `unknown`;
6. all applicable evidence healthy and score at least 80 → `ready`.

## Simulation

For each domain, simulate losing one through at most three hosts, bounded by `hostCount - 1`. Every host-loss combination at each depth is evaluated (up to 32 online hosts); the worst case compares remaining free capacity against memory used by powered-on protected workloads on the lost hosts plus a 10% reserve. Results are `unknown` when placement or memory evidence is incomplete or the safe combination bound is exceeded.

Provider-native depth supersedes only the capacity conclusion it explicitly proves:

- vSphere `currentFailoverLevel`;
- Xen `ha_plan_exists_for` and `ha_host_failures_to_tolerate`;
- Proxmox has no equivalent guarantee in the selected API evidence and remains estimated.

CPU compatibility, network reachability, storage attachment and application dependencies remain limitations unless independently proven.

## Recovery groups

Priorities are normalized to `highest`, `high`, `medium`, `low`, `lowest`, `disabled`, `unknown`. VMs are sorted deterministically by priority and display name. Only canonical opaque VM IDs are exposed. A disabled VM is unprotected. Proxmox protected resources remain `unknown` because its selected HA contract does not publish a portable restart order; unprotected guests are grouped as `disabled`. Xen and vSphere use native/default values when present.

## Provider collectors

### Proxmox

- `/cluster/status` for cluster identity and quorum;
- `/cluster/ha/status/current` for manager/LRM/service observations;
- `/cluster/ha/resources` for protected guests;
- existing node, VM and storage inventory for capacity and shared-storage evidence.

Missing optional HA endpoints produce typed unknown evidence, not a total endpoint failure. Base cluster/node inventory failure remains fatal.

### vSphere

Use PropertyCollector over `ClusterComputeResource` for `configurationEx.dasConfig`, `configurationEx.dasVmConfig`, summary, hosts and datastores. Standalone ESXi returns an unsupported snapshot without inventing a cluster. Host/VM/datastore reads remain bounded by the current client limits.

### Xen

XAPI reads existing pool, host, VM and SR records and preserves native HA runtime fields. Xen Orchestra requests only a bounded field projection. Raw Xen remains unsupported because a single-host CLI does not provide a managed pool HA contract.

## Cache, history and scheduler

- freshness TTL: 60 seconds;
- persistence bucket: five minutes;
- scheduled capture: every 15 minutes, leader-only;
- per-run endpoint concurrency: two;
- history API: 1–96 snapshots;
- refresh failures leave the last snapshot intact and return a sanitized error;
- history payloads are decrypted only after endpoint access is authorized.

## Test matrix

- migration up/down, constraints and encrypted payload;
- deterministic scoring, state precedence and semantic hash;
- Proxmox quorum/HA resource normalization plus optional endpoint loss;
- vSphere DAS parsing, standalone refusal and per-VM priority fallback;
- XAPI/XO HA fields and raw-Xen refusal;
- one/two-host loss simulation with native/estimated evidence;
- refresh dedupe, retention, cache and endpoint failure isolation;
- route flag, RBAC, host access, input bounds, auditing and error redaction;
- UI escaping, unsupported/unknown/empty/error states, refresh and history.
