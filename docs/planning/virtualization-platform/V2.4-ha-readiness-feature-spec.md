# V2.4 — HA inventory and readiness feature spec

**Status:** approved for implementation
**Release gate:** `DD_PROVIDER_HA_READINESS=false` by default
**Backlog:** B066–B067 and B074–B075
**Scope:** read-only evidence, history and simulations; no HA policy mutation

## Outcome

An authorized user can select a Proxmox, vCenter or managed Xen endpoint and see whether its HA domain is configured, healthy and able to tolerate host loss. The page separates native facts from conservative Docker Dash estimates, records bounded history, shows protected-workload coverage and groups the provider-declared recovery order. It never claims readiness when quorum, fencing, shared-storage, admission-control or placement evidence is missing.

## Contract

The versioned `1.0` snapshot contains:

- provider endpoint and capability evidence;
- one or more opaque HA domains;
- overall state (`ready`, `degraded`, `blocked`, `not_configured`, `unsupported`, `unknown`) and a bounded 0–100 score;
- host, powered-on workload and protected-workload counts;
- native/configured and observed failure tolerance when available;
- typed signals for HA enablement, quorum, heartbeat, fencing, shared storage, admission control, failover capacity and protection coverage;
- conservative N-host-loss scenarios with `pass`, `fail` or `unknown` evidence;
- recovery groups ordered by native restart priority, never a promised exact restart schedule;
- warnings and explicit provider limitations.

Native references, provider addresses and credentials are never returned. Topology snapshots are encrypted at rest.

## Provider matrix

| Provider plane | Native HA facts | Simulation | Recovery order |
|---|---|---|---|
| Proxmox VE cluster | Corosync quorum, HA manager/LRM/service state, configured HA resources | conservative host memory/free-memory model | protected/unprotected grouping; no fabricated native restart order |
| vCenter | `ClusterComputeResource` DAS configuration/summary, admission control, host monitoring, heartbeat datastores | native current failover level plus conservative model | per-VM DAS override or cluster default |
| standalone ESXi | HA unsupported | not available | not available |
| Xen XAPI pool | pool HA enabled/overcommitted/plan/failure-tolerance/statefile fields | native plan depth plus conservative model | `ha_restart_priority` / `ha_always_run` |
| Xen Orchestra | fields exposed by its pool/VM REST projection, with incomplete evidence called out | conservative only when sufficient data exists | exposed restart priority only |
| raw Xen | HA unsupported | not available | not available |

## API and RBAC

- `GET /api/providers/:hostId/ha/readiness` — permitted endpoint viewers; cached snapshot or live refresh when stale;
- `POST /api/providers/:hostId/ha/readiness/refresh` — admins with endpoint operate access; audited read refresh;
- `GET /api/providers/:hostId/ha/readiness/history?limit=...` — permitted endpoint viewers.

All routes remain unavailable while the release flag is off. Provider failures are sanitized and do not expose raw responses.

## Safety rules

1. `unsupported`, `unknown` and `not_configured` are distinct states.
2. Missing essential evidence never becomes `pass`.
3. A simulation is labeled estimated unless a provider publishes a native failover plan depth.
4. Capacity uses a reserve and cannot infer CPU/network/storage compatibility from memory alone.
5. Recovery priority is descriptive and does not imply dependency readiness or a guaranteed start time.
6. Snapshot writes use one bucket per endpoint/interval, encryption and bounded retention.
7. The scheduled collector is leader-gated, overlap-protected and isolates endpoint failures.
8. No endpoint in this batch changes HA, affinity, fencing or VM restart policies.
