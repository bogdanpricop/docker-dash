# V3.2 — Backup policy and retention feature specification

**Status:** implemented, validation and rollout pending

**Release gate:** `DD_PROVIDER_BACKUP_POLICIES=false` by default

**Execution boundary:** plan-only; no provider backup, prune, snapshot, restore, or repository mutation

## Outcome

Docker Dash can define, preflight, schedule, version, and audit portable backup policies against canonical V3.1 repositories and VM identities. A policy contains:

- explicit or dynamic workload scope by canonical ID, label, and power state;
- workload and disk exclusion intent;
- timezone-aware hourly, daily, weekly, or monthly schedules;
- crash/filesystem/application-consistency intent and failover behavior;
- portable newest-per-bucket keep-last/hourly/daily/weekly/monthly/yearly retention;
- required/preferred/none encryption and immutability intent;
- concurrency, bandwidth, and execution-window metadata;
- post-backup verification and restore-drill intent.

V3.2 persists deterministic plans, findings, plan hashes, and due-slot evidence. V3.3 is the first batch permitted to translate an accepted plan into a provider-native mutation.

## User stories

1. An administrator can create a disabled policy even when live evidence produces blockers, so the desired state can be reviewed and corrected.
2. An enabled policy is rejected when live repository or workload preflight has blockers.
3. A viewer can inspect policies and their immutable plan evidence without mutation access.
4. A scheduled policy produces at most one plan per local-time slot, including across DST repeats.
5. An unavailable provider produces a sanitized `blocked` plan instead of an invisible missed schedule.
6. Required encryption or immutability fails closed when capability evidence is false or unknown.
7. The retention preview never deletes a recovery point and clearly labels itself `mutationAuthorized:false`.

## Functional contract

### API

| Method | Path | Access | Effect |
|---|---|---|---|
| `GET` | `/api/providers/:hostId/backup-policies` | host viewer | list active policy definitions |
| `GET` | `/api/providers/:hostId/backup-policies/runs` | host viewer | list plan evidence |
| `POST` | `/api/providers/:hostId/backup-policies/preflight` | admin + operate | live read-only preflight and preview |
| `POST` | `/api/providers/:hostId/backup-policies` | admin + operate + writeable | create local policy state |
| `PUT` | `/api/providers/:hostId/backup-policies/:policyId` | admin + operate + writeable | update local policy state |
| `DELETE` | `/api/providers/:hostId/backup-policies/:policyId` | admin + operate + writeable | soft-delete local policy state |
| `POST` | `/api/providers/:hostId/backup-policies/:policyId/plan` | admin + operate + writeable | persist a manual plan, never run backup |

All responses use schema `1.0`. Native references, credentials, repository URLs, and provider error details are absent.

### Policy invariants

- `mode` is constrained in application and SQLite to `plan_only`.
- Repository and workload references must be canonical IDs scoped to the selected host.
- A key reference is an alias/vault path only; whitespace, PEM material, and arbitrary blobs are rejected.
- Explicit exclusions override all inclusions.
- Transient workload identities are excluded.
- Unknown tri-state capability evidence is not upgraded to support.
- Active policy names are unique case-insensitively per host.
- Policy hashes exclude enable/disable state; plan hashes exclude evaluation time and future occurrence display data.
- Soft deletion retains historical plan evidence.

## Retention semantics

The common preview is deliberately named `portable_newest`: it protects the newest recovery point in each selected time bucket, plus `keepLast`, provider-protected points, currently immutable points, and points without a usable timestamp. It only reports candidates.

This matches the “latest in each period” behavior described by current Proxmox Backup Server pruning. Xen Orchestra documents native GFS as retaining the oldest point in each period. A Xen preflight therefore emits `PROVIDER_GFS_SEMANTICS_DIFFER`; V3.3 must select and record a provider translation strategy instead of silently treating both behaviors as equivalent.

## Source-derived requirements

- Proxmox Backup Server provides keep-last/hourly/daily/weekly/monthly/yearly pruning, with the latest point retained in each period and ISO weeks starting Monday: [PBS pruning documentation](https://pbs.proxmox.com/docs/maintenance.html#pruning).
- Proxmox recommends restricting backup clients from deletion and doing prune jobs on PBS; verification is useful but is not sufficient ransomware protection by itself: [PBS storage and ransomware guidance](https://pbs.proxmox.com/docs/storage.html).
- PBS traffic control supports rate and time-frame constraints, which motivates portable bandwidth/window intent while leaving translation to V3.3: [PBS traffic control](https://pbs.proxmox.com/docs/network-management.html#traffic-control).
- Xen Orchestra supports schedule timezone/preview, smart VM selection, exclusions, concurrency, encryption, GFS, and health checks: [XO backup concepts](https://docs.xen-orchestra.com/backups).
- XO states that losing the remote encryption key makes encrypted backups inaccessible; the UI therefore accepts only a key reference and never key material: [XO backup encryption](https://docs.xen-orchestra.com/backups#backup-encryption).
- XO immutability is controlled on the backup host and duplicate schedules can accumulate protected backups, reinforcing deterministic slot deduplication: [XO immutability](https://docs.xen-orchestra.com/xo5/immutability).

## Acceptance criteria

- Migration creates policy and plan-evidence tables with FKs, checks, and partial uniqueness.
- Every enabled create/update performs live recovery repository and VM inventory preflight.
- Repository mismatch, inaccessible/disabled state, empty scope, and required unproven security capability block enablement.
- Inventory truncation, missing explicit VMs, deferred disk exclusions, consistency evidence, and provider GFS semantic differences are visible findings.
- A leader-gated minute wake-up records due plans and deduplicates local-time slots.
- Provider unavailability at a due slot records a blocked, sanitized plan.
- UI exposes authoring only to administrators and labels the entire feature plan-only.
- Focused and full automated suites pass; staging migration, flag, HTTP, authenticated API, DB integrity, and container health are verified.

## Explicit non-goals

- Creating or updating native backup jobs or schedules.
- Starting a backup, snapshot, verification, prune, or restore operation.
- Resolving provider-native disk identifiers.
- Managing or transmitting encryption key material.
- Claiming immutable storage based only on policy intent.
- Treating VM snapshots as recovery-point backups.
