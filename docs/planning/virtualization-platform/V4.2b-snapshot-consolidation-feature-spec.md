# V4.2b — vSphere snapshot consolidation feature specification

**Status:** shipped in v8.24.0 (2026-07-28)

**Release gates:** `DD_PROVIDER_VM_SNAPSHOTS=false` and `DD_PROVIDER_VM_SNAPSHOT_CONSOLIDATION=false` by default.

## Outcome

Docker Dash can now queue a VMware vSphere `ConsolidateVMDisks_Task` only when the live VM runtime reports `consolidationNeeded=true`. The action is deliberately separate from snapshot deletion because it can generate material datastore I/O and may be needed after a failed or incomplete provider-side snapshot operation.

## Safety contract

1. The endpoint is vSphere-only; Proxmox, XenAPI, Xen Orchestra and raw Xen advertise the capability as unsupported.
2. A fresh VM read must report `runtime.consolidationNeeded=true`; absent or false evidence blocks both preview and worker execution.
3. General snapshot release and the dedicated consolidation release flag must both be enabled.
4. An administrator with host `operate` access receives a short-lived semantic preflight and types the exact VM display name before submission.
5. Submission creates one non-idempotent durable operation under the existing per-VM lock; retries are never replayed after ambiguous provider failure.
6. Completion requires the durable native task plus a fresh VM read showing `runtime.consolidationNeeded=false`. A completed task alone is not success.

## API

| Method | Path | Access | Effect |
|---|---|---|---|
| `POST` | `/api/providers/:hostId/virtual-machines/:vmId/snapshots/consolidate/preflight` | admin + host operate | read-only plan |
| `POST` | `/api/providers/:hostId/virtual-machines/:vmId/snapshots/consolidate` | admin + host operate | queues the reviewed vSphere task |

## Explicit exclusions

- snapshot deletion, bulk consolidation, automatic remediation, scheduling and policy-driven execution;
- filesystem repair, guest commands, datastore relocation, QoS changes and provider CLI/shell fallbacks;
- treating a missing runtime field, task completion or a snapshot list alone as consolidation proof.
