# V3.3 — Backup execution and verification deep specification

## 1. Boundaries and invariants

- V3.2 remains the policy/plan authority; its SQLite `mode` remains constrained to `plan_only`.
- V3.3 adds a separate `execution_mode`, default `disabled`. No migration upgrades an existing policy automatically.
- Only an accepted `planned` run can become an execution.
- A fresh plan is calculated immediately before persistence and must have the same hash.
- Volatile inventory observation timestamps are excluded from plan hashing; capability/status/scope evidence remains included.
- A provider task result is necessary but insufficient. A new V3.1 recovery point is mandatory.
- `retentionMutationAuthorized` is always false in schema, service, handler, route, audit, and UI evidence.
- Public identifiers are canonical. Native VM, repository, recovery-point, and task references remain encrypted at rest and server-side only.

## 2. Authorization matrix

| Operation | Auth | Host scope | Global write gate | Typed confirmation | Idempotency |
|---|---|---|---|---|---|
| list/get executions | authenticated | view | no | no | n/a |
| authorize/disable | admin | operate | yes | exact policy name when enabling | n/a |
| manual execute | admin | operate | yes | exact policy name | required header |
| scheduled execute | system leader | policy host | policy/operation gates | prior per-policy authorization | deterministic plan-run key |
| cancel | admin | operate | yes | exact policy name | operation state machine |

Disabling execution prevents new parent creation. Already accepted durable operations continue to reconciliation so an operator cannot turn an ambiguous provider mutation into invisible state. Emergency-stop behavior remains owned by the common operation policy.

## 3. Idempotency and locking

Parent idempotency hash:

```text
sha256(policyId + "|" + Idempotency-Key)
```

The stored request hash covers policy ID, supplied plan run/hash, and trigger. Reuse with different intent is `409 IDEMPOTENCY_KEY_CONFLICT`.

Child key:

```text
backup:<executionId>:<canonicalWorkloadId>
```

Child locks:

```text
resource:<canonicalWorkloadId>
repository:<canonicalRepositoryId>
```

The operation is deliberately `idempotent:false`. A transport interruption after submission moves it to reconciliation and never resubmits `vzdump`.

## 4. Create sequence

```text
request
  → release/policy/RBAC/confirmation/idempotency gates
  → load or create immutable V3.2 plan run
  → live V3.2 preflight
  → exact plan-hash match
  → live backup.run capability probe
  → execution-specific blockers
  → complete recovery-point baseline
  → atomic parent + child item insert
  → bounded child dispatch
  → durable provider-operation worker
```

Execution-specific blockers are:

- provider mutation not conformance-tested;
- capability not `supported|conditional`;
- consistency other than `crash`;
- requested disk exclusions;
- execution outside the configured local-time window;
- required verification without repository capability `true`;
- truncated baseline inventory.

## 5. Child execute and reconcile

### Execute

1. decrypt canonical VM and repository native references scoped to the endpoint;
2. read current Proxmox cluster VM and repository inventories;
3. require the VM to exist, remain non-template, be unlocked, and retain the expected guest type;
4. require the selected repository to remain enabled and accessible;
5. require node match for local repository identity;
6. translate Mbps to rounded KiB/s (`Mbps × 125`);
7. submit a single-VM `vzdump` task;
8. bind the UPID using encrypted native-task storage;
9. return `reconciling`.

### Reconcile

1. read UPID status;
2. keep `reconciling` while the task is active;
3. fail on a non-`OK` terminal result;
4. after `OK`, fetch current canonical recovery points for repository + workload;
5. reject truncated discovery inventory;
6. select a non-baseline point created no earlier than two minutes before operation start;
7. wait up to 30 minutes for eventual inventory visibility;
8. return `unknown` if no point appears;
9. return `succeeded` with canonical point ID and its current verification state when observed.

The two-minute allowance tolerates bounded clock skew without allowing a known baseline point to satisfy the proof.

## 6. Verification

When `afterBackup=false`, a child finishes after task + point proof and records the observed verification state without upgrading it.

When `afterBackup=true`:

- `verified` → `succeeded`;
- `failed` → `failed / BACKUP_VERIFICATION_FAILED`;
- `unknown|unverified|stale` → `verification_pending`;
- a leader-gated refresh rereads live V3.1 inventory;
- truncated or failed refresh preserves pending state;
- crossing `maximumUnverifiedHours` → `unknown / BACKUP_VERIFICATION_TIMEOUT`.

Verification-pending items do not consume backup concurrency because the provider backup task has already ended.

## 7. Parent reconciliation

Each minute, the leader:

1. maps terminal child operation state/result into item state;
2. refuses a child success without a syntactically valid canonical recovery-point ID;
3. refreshes pending verification evidence once per parent;
4. dispatches more queued items up to `maxConcurrent`;
5. recomputes authoritative counts from item rows;
6. derives parent state;
7. emits one terminal system audit event.

Parent derivation priority:

1. queued/running → `running`;
2. verification pending → `verification_pending`;
3. all success → `succeeded`;
4. some success → `partial`;
5. any failed → `failed`;
6. any unknown → `unknown`;
7. all cancelled → `cancelled`.

## 8. Scheduling

V3.2 first persists the timezone/due-slot plan. V3.3 scans scheduled `planned` runs whose policy has `execution_mode=scheduled` and no parent execution. The deterministic key `scheduled:<planRunId>` makes repeated leader wake-ups harmless.

The scheduler uses the accepted plan run, reruns live preflight, and refuses drift. It does not retry by mutating the old plan; the failure remains visible in logs and the original plan evidence remains immutable.

## 9. Cancellation

- queued items become `cancelled` without provider access;
- running operations receive the common durable cancellation request and Proxmox task stop call;
- a cancellation that cannot be confirmed follows the operation engine to `unknown`;
- verification-pending items become `unknown`, because the backup exists but verification was abandoned;
- completed recovery points are never removed;
- terminal parents cannot be cancelled again.

## 10. Change control and recovery

Policy field updates and deletion are blocked while a parent is `queued`, `running`, or `verification_pending`. This prevents the reconciler from applying mutable concurrency/verification semantics to an accepted execution. Execution authorization may still be set to `disabled` to stop new work.

Migration 119 is additive. Its `down` removes execution tables but deliberately retains additive authorization columns because rebuilding the policy table during an emergency downgrade is riskier. They remain fail-closed and inert for older code.

On application restart:

- the common operation engine recovers expired child leases;
- the parent cron discovers active parents and resynchronizes child states;
- unique plan-run/idempotency/item constraints prevent duplicate reconstruction;
- previous Docker image and database/config backup remain the rollback anchors.

## 11. Failure matrix

| Failure | Result |
|---|---|
| provider capability unavailable | create blocked, no parent |
| live plan drift | `409 BACKUP_PLAN_CHANGED`, no mutation |
| duplicate identical key | existing parent returned |
| duplicate conflicting key | `409 IDEMPOTENCY_KEY_CONFLICT` |
| local repository on other node | child failed before submit |
| transient submit response after possible acceptance | child reconciles, no replay |
| native task failed | child failed |
| native task OK, point absent | reconcile then unknown |
| point observed, verification pending | verification_pending |
| verification failed | failed |
| verification deadline crossed | unknown |
| inventory truncated | baseline blocked or pending evidence retained |
| restart during operation | lease recovery + native task reconciliation |
| policy edit/delete during execution | `409 BACKUP_EXECUTION_ACTIVE` |
| cancel provider confirmation ambiguous | unknown |

## 12. Telemetry and audit

Audit actions:

- `provider_backup_execution_authorized`;
- `provider_backup_execution_disabled`;
- `provider_backup_execution_started`;
- `provider_backup_execution_deduplicated`;
- `provider_backup_execution_cancel_requested`;
- `provider_backup_execution_completed`.

Payloads contain host/policy/execution/plan IDs, modes, states, and counts. They explicitly record `retentionMutationAuthorized:false`. Provider-native identifiers and credentials are excluded.
