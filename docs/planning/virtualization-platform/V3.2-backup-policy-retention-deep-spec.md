# V3.2 — Backup policy and retention deep specification

## Architecture

```text
admin draft
   │
   ▼
strict bounded validation ── canonical policy hash
   │
   ├── V3.1 repository/recovery-point inventory (live, repository-filtered)
   └── provider VM inventory (live, max 500)
             │
             ▼
   scope + capability + GFS preflight
             │
             ├── blockers/warnings
             ├── deterministic plan hash
             └── execution.authorized = false
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
 local policy definition       immutable plan evidence
 provider_backup_policies      provider_backup_policy_runs
```

No edge from V3.2 reaches a provider mutation adapter.

## Persistence model

### `provider_backup_policies`

The row owns host/repository scope, local enablement, seven bounded JSON documents, and a SHA-256 policy hash. JSON is used because the nested common contract will evolve independently of vendor schemas. SQLite checks retain the highest-risk invariants: canonical-looking IDs, `plan_only` mode, hash width, and status domains.

The repository FK is `RESTRICT`: a policy may not silently lose its target. Host deletion still cascades the entire host-scoped catalog. Deletion is soft at the policy layer so evidence remains queryable.

### `provider_backup_policy_runs`

A “run” in V3.2 is a completed planning event, not a backup operation. States are only `planned`, `blocked`, and reserved `superseded`. `(policy_id, slot_key)` is unique. Evidence includes both policy and plan hashes, full safe plan JSON, findings, trigger, actor, and completion time.

## Validation and bounds

| Field | Bound |
|---|---:|
| policy name | 3–120 characters |
| description | 500 characters |
| explicit/excluded workloads | 500 each |
| label predicates | 16 per selector |
| disk exclusion intents | 32 |
| recovery points used per live preview | 500 |
| policies evaluated per tick | 20 |
| returned policies/runs | 200 |
| future occurrences | 10, search horizon 400 days |
| retention tier counts | tier-specific hard limits |
| concurrency | 1–32 |
| bandwidth | 1–100,000 Mbps or unlimited |

The server-wide 2 MiB JSON body limit remains effective. Plans project only canonical IDs, display names, power states, repository status/capabilities, and retention evidence. Resource labels are evaluated in memory and are not copied into the persisted plan.

## Schedule model

The accepted recurrence set is intentionally smaller than arbitrary cron:

- `hourly`: quarter-hour minute;
- `daily`: local hour and quarter-hour minute;
- `weekly`: plus weekday `0..6`;
- `monthly`: plus day `1..28` to avoid ambiguous missing dates.

Timezone must be accepted by `Intl.DateTimeFormat` as an IANA zone. A slot key is derived from the local wall-clock components and timezone, for example `2026-10-25T02:15@Europe/Bucharest`. Repeated DST instants collapse to the same local key and the database uniqueness constraint provides a second dedupe layer.

Upcoming occurrences are computed on 15-minute UTC boundaries across a bounded 400-day horizon. This is deterministic and dependency-free for the supported recurrence set.

## Scope resolution

1. Read at most 500 normalized VMs from the host.
2. Include when `includeAll`, explicit canonical ID, or the smart-selector expression matches.
3. Apply explicit and label exclusions after inclusion.
4. Remove transient identities.
5. Sort selected items by canonical ID.
6. Report explicit IDs absent from the current inventory.

Smart selectors support label equality and normalized power state with `all`/`any` composition. Provider tags already normalize into the common label map. Disk exclusions remain intent because V3.2 lacks a stable common disk identity; claiming that a free-form disk label was enforced would be unsafe.

## Security capability logic

Repository capability values are tri-state (`true`, `false`, missing/unknown):

| Requirement | true | false | unknown |
|---|---|---|---|
| none | pass | pass | pass |
| preferred | pass | warning | warning |
| required | pass | blocker | blocker |

`required` encryption also requires a safe key alias/path. Docker Dash never accepts or stores key material. Policy intent does not prove that existing or future points are encrypted or immutable; actual recovery points keep their own V3.1 evidence.

## Portable GFS preview

Points are ordered by `createdAt DESC`, then canonical ID. Protection is the union of:

1. newest `keepLast` points;
2. newest point in each distinct configured hourly/daily/weekly/monthly/yearly bucket;
3. provider-declared protected points;
4. points with a future immutable-until timestamp;
5. points whose timestamp cannot be safely classified.

Everything else is a candidate only. Candidate output grants no prune permission. Weeks use the policy `weekStartsOn` value and buckets use the schedule timezone.

Native differences remain explicit. Current PBS documents newest-per-period pruning, while XO documents oldest-per-period GFS. The V3.3 adapter must either translate portable semantics itself or select provider-native semantics and require renewed approval with a changed plan hash.

## Failure behavior

- Validation errors: typed `400 INVALID_BACKUP_POLICY`.
- Execution mode: `409 BACKUP_EXECUTION_DISABLED`.
- Enabled policy with blockers: `409 BACKUP_POLICY_PREFLIGHT_BLOCKED` with safe findings.
- Unknown/untrusted server error: generic 500 body.
- Scheduled live-read failure: persisted blocked plan containing only a validated error code and generic message.
- Duplicate due slot: deduplicated by last slot and DB uniqueness.
- Disabled feature: 404; no list, authoring, planning, deletion, or scheduled processing.

## Authorization and audit

Policy and run reads require host view. Preflight and local policy mutations require administrator plus host operate; writes also pass the global writeability middleware. Audit events record host, canonical policy/repository IDs, hashes, state, counts, actor, IP, and `executionAuthorized:false`. Provider details and key references are excluded from audit payloads.

## V3.3 hand-off contract

V3.3 may consume a V3.2 plan only after it:

1. reloads the policy and verifies `policyHash`;
2. reruns live repository, scope, consistency, and security preflight;
3. selects an explicit provider translation and records semantic differences;
4. creates a durable idempotent parent operation;
5. keeps backup creation and retention pruning as separately observable phases;
6. never prunes when backup creation or verification is failed/unknown;
7. proves the produced recovery point back through V3.1 inventory.
