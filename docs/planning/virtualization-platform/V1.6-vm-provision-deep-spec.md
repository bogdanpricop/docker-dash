# V1.6 Deep spec — durable VM provisioning

## Contract public

Preflight body:

```json
{
  "name": "app-01",
  "mode": "auto",
  "storageId": "ddr_storage_<26 hex>",
  "targetNode": null
}
```

`storageId` este opțional și canonical. `targetNode` este opțional și acceptat numai de Proxmox. Preflight returnează template-ul public, `requested/effective` mode, storage candidates, blockers, warnings, typed confirmation, `validUntil` și `planHash` SHA-256 peste semantica planului.

Submit-ul repetă exact body-ul și adaugă:

```json
{
  "planHash": "<64 hex>",
  "confirm": true,
  "confirmName": "app-01"
}
```

Headerul `Idempotency-Key` are 8–200 caractere ASCII vizibile. Răspunsul `202` conține planul public și operația, nu task reference-ul nativ.

## Authorization și release gates

- auth obligatoriu;
- rol `admin`;
- effective host access `operate`;
- middleware `writeable` pentru submit;
- `DD_PROVIDER_SDK_V2=true` și `DD_PROVIDER_VM_PROVISIONING=true`;
- operation policy global/provider/host trebuie să fie `active`;
- capability live `vm.create` trebuie să fie supported/conditional.

Preflight rămâne accesibil când flag-ul de provisioning este OFF, pentru a arăta blocker-ul `RELEASE_DISABLED`. Submit-ul nu poate ocoli re-preflight-ul.

## Identity și secret boundary

Operația are:

- `resource.kind=artifact`;
- `resource.id=dda_art_*`;
- request encrypted: numai IDs canonice, name, mode și safe placement;
- native task encrypted separat de operation engine;
- lock `resource:<artifactId>`;
- lock `provider-name:<sha256(host|lowercase name)[0..32]>`.

Operation engine păstrează regex-ul resurselor comune neschimbat și adaugă exclusiv perechea `artifact` + `dda_art_*`. `artifact-catalog.resolveArtifact()` cere host scope, verifică provider/kind/JSON integrity și decriptează native ref numai în server process.

## State machine

```text
queued
  → running / pre-submit revalidation
  → reconciling: clone-task
      → Proxmox/vSphere: post-verify
      → XAPI: provision-ready → provision-submit → provision-task → post-verify
  → succeeded | failed | unknown | cancelled
```

Handlerul este `idempotent=false`, `retryPolicy=none`. O eroare tranzitorie după submit mută operația în reconciliation, nu în execute retry. Dacă task ref nu a fost persistat înainte de întrerupere, handlerul caută numele/ID-ul țintă; nu retrimite clone-ul. După o oră fără evidence determinist, rezultatul este `unknown` și lock-urile rămân active.

## Provider mapping

### Proxmox VE

1. revalidează `qemu/<template vmid>` și node;
2. alocă `cluster/nextid` imediat înainte de submit;
3. mapează storage canonical la live `storage` name;
4. validează target node în `nodes`;
5. trimite `POST nodes/{node}/qemu/{vmid}/clone` cu `full=1|0`;
6. persistă UPID + submit node;
7. verifică terminal `status=stopped, exitstatus=OK` și VMID/nume în inventory.

Template-urile `template=1` sunt excluse din common runnable VM inventory.

### VMware vSphere/ESXi

1. revalidează `config.template=true`;
2. citește `parent`, `resourcePool` și source `datastore` prin PropertyCollector;
3. datastore explicit trebuie să fie accesibil și să nu fie în maintenance; default este source datastore;
4. trimite `CloneVM_Task` cu `powerOn=false`, `template=false`;
5. persistă Task MoRef și verifică `info.state`/`info.result`;
6. succesul final cere VM unică în common inventory.

Linked clone rămâne blocker pentru că are nevoie de snapshot/disk backing semantics care nu trebuie deduse implicit.

### XAPI

- `auto` devine `linked`;
- linked: `Async.VM.clone(templateRef, name)`;
- full: `Async.VM.copy(templateRef, name, SR)`; dacă lipsește storage, se cere un singur pool default SR;
- clone/copy task result furnizează VM ref;
- handlerul persistă `provision-ready`, apoi `provision-submit` înainte de apelul `Async.VM.provision(vmRef)` și, după răspuns, task envelope-ul;
- după un răspuns întrerupt, `VM.get_record.current_operations` recuperează task-ul; dacă submit-ul nu poate fi confirmat, mutația nu este retrimisă și operația devine `unknown` la deadline;
- după provision task, VM-ul este re-citit și normalizat.

### Xen Orchestra și raw Xen

XO poate lista template-uri, dar controllerul REST oficial curent nu are acțiune `vm-template/instantiate`. Capability rămâne unsupported. Raw Xen nu are template identity/task workflow portabil și rămâne unsupported.

## Failure modes

| Failure | Rezultat |
|---|---|
| artifact dispărut/convertit | fail înainte de submit |
| nume existent | preflight blocker și pre-submit fail |
| storage/node invalid | blocker sau fail înainte de clone |
| provider reject | failed cu cod sanitizat |
| transport întrerupt după submit | reconciliation-only |
| task pending | lease renewal + bounded polling |
| task failed | failed, fără replay |
| task success, inventory lag | post-verify polling |
| VM lipsă după deadline | unknown, lock păstrat |
| cancel Proxmox confirmat | cancelled |
| cancel vSphere/XAPI neconfirmat | unknown |

## Observability și audit

- audit `provider_vm_provision_submit` include provider, host, operationId, targetName, cloneMode, canonical storage și `startAfterCreate=false`;
- Activity Center arată owner, state, stage, attempt, progress și task presence; native ref rămâne ascuns;
- events au numai safe bounded details;
- succesul returnează canonical VM ID, display name, power state, mode și `verified=true`.
