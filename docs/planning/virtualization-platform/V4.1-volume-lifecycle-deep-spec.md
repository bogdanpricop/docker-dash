# V4.1 — Volume lifecycle deep specification

## Domain model

`provider_managed_volumes` records the durable ownership proof for a volume created through this workflow: opaque ID, endpoint, canonical VM, provider type, encrypted native backing reference, portable storage/bus/unit metadata, capacity, lifecycle state, create operation and timestamps. Its public projection never contains the encrypted reference.

The live disk is still authoritative. A managed record may be `creating`, `attached`, `detached`, `moving`, `deleting`, `deleted` or `unknown`. The service correlates it only through the server-side native reference and the same deterministic portable disk identity used by V1.9. Missing or ambiguous correlation becomes `unknown`; it does not authorize cleanup.

## Action contracts

### Create and attach

The request contains size bytes, portable bus, optional unit, canonical target storage, provisioning mode and a bounded label. Preflight validates storage accessibility, accepted disk content, free capacity plus configured headroom, size/allocation bounds and an unused device slot. Execution creates exactly one backing and one attachment through the provider's documented API, then re-reads hardware. Ownership becomes `attached` only after a unique positive match.

### Detach and retain

The request identifies one opaque disk. Preflight and execution reject optical, boot, read-only and shared devices. The provider operation removes or unplugs the attachment without a backing-destroy instruction. A managed record transitions to `detached` only after the disk is absent from the VM and the provider returns a retained backing identity.

### Resize

The requested size must be strictly greater than the observed capacity and within the provider/storage maximum. Online execution additionally requires provider evidence for that exact device; otherwise the VM must be stopped. Post-verification requires observed capacity greater than or equal to requested capacity. The result always includes `guestExpansionRequired=true`.

### Move

The target storage must differ, be accessible, support the disk content and have requested capacity plus headroom. Execution uses a native move/copy/relocation primitive and retains the original until provider completion. Post-verification requires the disk to resolve uniquely on the target storage. Ownership metadata is updated only after verification.

### Delete backing

Delete is a distinct action, not a detach option. The disk/backing must be Docker Dash-owned, detached, unshared, non-boot, outside every current VM attachment, and protected by a verified recovery point no older than the configured deletion window. Existing VM snapshots or replication evidence block deletion unless the provider proves no dependency. The caller types `DELETE VOLUME <managed label>` and the second release flag must be enabled. The record is tombstoned after provider absence is positively verified.

## Preflight and hashing

Every plan binds schema version, endpoint/provider, canonical VM/disk/managed-volume IDs, action, requested values, observed disk and power state, storage capacity evidence, snapshot/dependency digest, capability state/constraints, policy result, blockers, warnings and a five-minute validity boundary. Presentation timestamps and secrets are excluded. Submission must supply the exact SHA-256 plan hash and explicit confirmation; detach/move/resize use the exact VM display name and delete uses the stronger volume phrase.

## Operation semantics

All actions use `vm.disk` durable operations and a VM-level resource lock. Create also locks its target storage; move locks source and target storage; delete locks the managed volume. Handlers have no automatic replay because disk mutations are not generally idempotent. On restart they reconcile a stored native task. When a provider documents a synchronous configuration call, the handler proceeds directly to post-verification and never repeats the call after an ambiguous failure.

The operation result contains portable IDs, verified state, capacity/storage facts and guest guidance only. Native tasks are stored encrypted through the existing operation engine representation and are never returned as provider references.

## Provider transports

- Proxmox QEMU uses the configuration digest when supplied. Create/attach and resize can be synchronous but require live config verification. Storage move uses the native UPID. Detach retains the backing as an `unusedN` entry. Permanent cleanup is restricted to a correlated owned unused entry.
- vSphere builds incremental `VirtualDeviceConfigSpec` requests, fully specifies the target device, and uses `fileOperation=destroy` only for an owned-delete plan. Resize uses `ReconfigVM_Task`. Move uses `RelocateVM_Task` and a `VirtualDiskLocator` keyed to the device.
- XenAPI resolves VM/VBD/VDI/SR opaque references only within the adapter. Mutations use `Async.*` methods where available. VBD allowed operations are advisory; current record state is revalidated. Current XenAPI releases do not justify a universal online-resize claim, so a running VM is blocked unless the endpoint explicitly proves it.
- Xen Orchestra and raw Xen advertise an explicit unsupported reason. No fallback to undocumented RPC or shell tools exists.

## Failure and recovery

- stale plan, identity, storage, power or dependency evidence fails before mutation;
- provider timeout after an uncertain submit transitions to reconciliation/unknown and never replays create/delete;
- a partial XAPI create remains `unknown` with ownership evidence and requires explicit operator reconciliation;
- failed move leaves ownership on the last positively verified storage;
- detach verification failure leaves the record attached/unknown, never detached by assumption;
- delete verification failure leaves a tombstone pending and never claims data removal;
- cleanup jobs may report stale managed records but cannot mutate provider state without a fresh interactive plan.
