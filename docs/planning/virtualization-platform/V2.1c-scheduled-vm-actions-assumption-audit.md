# V2.1c — Scheduled VM actions assumption audit

| Assumption | Evidence / decision | Result |
|---|---|---|
| B045 can reuse the legacy container scheduler | `scheduled_actions` targets container names and bypasses provider operation preflight | Rejected |
| Schedule submission needs a new executor | VM power and snapshot services already create durable, locked, idempotent provider operations | Rejected; reuse operation core |
| `stop` means forced power-off | Existing common VM action `shutdown` provides guest coordination and exposes blockers | Rejected; map to `shutdown` |
| A scheduled snapshot includes retention | B045 only requests snapshot scheduling; retention already has a separate policy feature | Rejected; create only |
| UTC is sufficient | Market requirement explicitly includes blackout windows and operator-local schedules | Rejected; IANA timezone required |
| DST ambiguity may execute twice | Two UTC instants can share one local wall minute | Rejected; explicit `first`, `second`, or `skip` policy |
| HTTP blackout middleware protects background work | Background jobs do not pass through HTTP middleware | Rejected; query governance blackout evidence in the scheduler |
| Leader-only execution alone prevents duplicates | A leader can change after dispatch or crash before updating schedule state | Rejected; database slot uniqueness plus child idempotency are authoritative |
| VM name is a durable target | Names can change and collide | Rejected; canonical stable VM ID is authoritative, name is confirmation/display evidence |
| Unknown provider outcome is safe to retry | Retrying could duplicate a provider mutation | Rejected; persist `unknown`, hold the schedule lock, require operation resolution |
