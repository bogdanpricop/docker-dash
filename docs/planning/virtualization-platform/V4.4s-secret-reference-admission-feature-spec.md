# V4.4s — Automatic secret-reference admission

**Status:** v8.91.3 release candidate; rollout pending

**Market feature:** B168

## Outcome

The hash-only secret-reference validator introduced in v8.83.0 is now reused
automatically by the application write paths that accept infrastructure
manifests, infrastructure workflow jobs and onboarding template documents.

Admission rejects inline secret fields, credential-bearing URLs, private keys
and secret-shaped environment assignments before the resource is persisted.
Approved manager URIs, exact `${ENVIRONMENT_VARIABLE}` references, Kubernetes
`secretKeyRef`/`secretRef` forms and named Compose/Kubernetes secret references
are recognized without returning their raw values in admission evidence.

## Integration surfaces

- infrastructure manifest validate/save, change-plan and revalidation flows;
- infrastructure workflow creation and compensation inputs;
- onboarding custom and built-in template validation;
- provider security-lifecycle validation, which retains its endpoint-scoped,
  hash-only persistence contract.

Successful manifest and workflow write audits include only the admission
document hash, reference count and valid state. Rejected requests return 422
with finding paths/codes and hashes; neither the submitted document nor raw
reference values are copied into admission evidence.

## Safety and compatibility

- no provider, network or external call is started;
- the 256 KiB document bound remains enforced before traversal;
- existing onboarding template policy stays stricter and continues to reject
  every secret-shaped key, including reference-shaped template fields;
- valid manifests/workflows remain backward-compatible, while inline secrets
  hidden in environment string arrays are now rejected;
- B168 remains `Partial` until integrated browser smoke can be recorded.

## Verification

- `src/__tests__/secret-reference-admission.test.js` covers all supported
  reference forms, inline-secret rejection, safe evidence and size bounds;
- infrastructure automation tests cover automatic manifest/job enforcement;
- provisioning template tests cover inline assignments in unknown fields;
- provider lifecycle tests retain the persisted hash-only contract.
