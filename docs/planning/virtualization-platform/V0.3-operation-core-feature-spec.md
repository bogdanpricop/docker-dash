# V0.3 Feature spec — durable provider operation core

## Problemă

Operațiile lungi existente folosesc tabele și workers diferite, iar provider mutations viitoare nu pot presupune că procesul Docker Dash rămâne pornit până la răspunsul final. Timeout-ul providerului poate însemna succes, eșec sau rezultat necunoscut; retry-ul fără idempotency și locks poate dubla o mutation.

## Outcome

V0.3 introduce nucleul persistent pentru toate operațiile Provider SDK viitoare. Nucleul persistă request-ul criptat, state machine-ul, progress/events, task-ul nativ, retry-ul, lease-ul și resource locks. După restart, operațiile întrerupte intră în reconciliation, nu sunt relansate orbește.

## State machine

```text
queued → running → succeeded
               ↘ failed
               ↘ waiting_retry → running
               ↘ reconciling → succeeded | failed | unknown
queued/running/reconciling → cancel_requested → cancelled | unknown
unknown → succeeded | failed | cancelled  (rezoluție manuală auditată)
```

Stările terminale sunt `succeeded`, `failed`, `cancelled` și `unknown`. `unknown` nu permite retry automat.

## Contract intern pentru handlers

Un handler este înregistrat numai din cod și declară:

- `type` stabil, de exemplu `vm.power.start`;
- `execute(context)`;
- opțional `reconcile(context)` și `cancel(context)`;
- timeout și retry policy;
- dacă operația este idempotentă.

Nu există endpoint generic de creare care să accepte un handler arbitrar de la client. Provider routes din V1.x vor crea operații prin API-ul intern allowlisted.

## API Activity Center

```http
GET  /api/operations?limit=100&state=running&hostId=7
GET  /api/operations/:id
GET  /api/operations/:id/events
POST /api/operations/:id/cancel
POST /api/operations/:id/resolve

GET /api/operations/policies
PUT /api/operations/policies/:scopeType/:scopeKey
```

List/detail/events sunt filtrate prin host permissions. Cancel necesită `operate`; rezolvarea unei stări `unknown` și control policies necesită admin.

## Control policies

- global `read_only` blochează provider operations, automation și routes care folosesc middleware-ul standard `writeable`;
- `emergency_stop` poate fi global, per provider sau host, anulează queued work și cere cancel pentru running work;
- `frozen` oprește operații noi într-un interval ISO explicit;
- `active` elimină blocarea pentru scope-ul respectiv;
- modificarea policy este auditată și rămâne disponibilă pentru recovery chiar în read-only mode.

## Durability și safety

- request payload și native task ref sunt AES-256-GCM encrypted at rest;
- idempotency key este stocat numai ca SHA-256 scope hash;
- lock scopes sunt canonical IDs sau endpoint scopes, cu lease și expiry;
- retry este permis numai pentru erori tranziente și handlers idempotente;
- timeout-ul folosește reconcile când există, altfel produce `unknown`;
- progress/events/result/errors sunt bounded și redacted;
- lease-ul expirat după restart mută operația în `reconciling`;
- worker-ul are concurrency cap și timers `unref`.

## Acceptance criteria

1. operația și events supraviețuiesc recreării engine-ului;
2. același idempotency key returnează aceeași operație;
3. două operații nu pot deține simultan același lock;
4. transient failure intră în bounded retry, permanent failure nu;
5. timeout/restart nu relansează mutation fără reconciliation;
6. cancel este confirmat de handler sau devine `unknown`;
7. native task ref și request nu apar în API sau plaintext DB;
8. global/provider/host policy blochează corect;
9. Activity Center respectă RBAC și host access;
10. manual resolution este limitată la `unknown` și auditată;
11. worker startup/shutdown este simetric;
12. legacy jobs continuă să funcționeze neschimbat.
