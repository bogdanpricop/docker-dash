# V3.6 — Replication and DR runbooks deep specification

## Domain model

`provider_dr_protection_groups` owns one source endpoint, one recovery endpoint, a strategy, RPO/RTO objectives, canonical placement/network mappings, authorization metadata and soft-delete state. `provider_dr_group_members` owns at most 64 canonical source VMs, authoritative display-name snapshots, boot stages, dependency edges and optional backup/drill policy links.

`provider_dr_runs` stores only non-mutating rehearsals in this slice. Each row freezes the group revision, runbook mode, semantic plan hash, bounded evidence, evidence hash, compliance result and measured maxima. A blocked rehearsal is retained as evidence; deletion of a group never deletes its runs.

## Strategies

- `provider_replication`: requires live replication evidence for every member. Proxmox jobs are explicitly intra-cluster asynchronous copies.
- `backup_restore`: requires a verified canonical recovery point for every member and measured restore-drill evidence for automated-test compliance.
- `hybrid`: evaluates both and selects neither implicitly; every member must name its intended recovery source.

No strategy changes the semantics of a provider. Recovery plans compile from evidence; they do not infer credentials, licensing, fencing or network ownership.

## Graph validation

Members have a stable canonical VM ID, `bootStage` from 1 to 20 and zero or more `dependsOn` VM IDs. The validator rejects self-dependencies, missing references, duplicate edges, cycles and an edge whose dependency has a later boot stage. A deterministic topological sort uses `bootStage`, normalized display name and canonical ID as tie breakers.

Failover startup follows dependency order. Source isolation and failback shutdown use reverse dependency order. Independent members in the same stage form a bounded wave, but the plan does not promise concurrent provider execution.

## Evidence collection

For each member, the rehearsal reads:

1. canonical source identity and last normalized VM snapshot;
2. the newest verified recovery point and its age;
3. the newest successful automated restore-drill result and measured assertion RTO;
4. matching provider-replication inventory, when supported;
5. target placement and network mapping identity ownership;
6. current provider capabilities and endpoint reachability.

The service never decrypts or returns native identities to routes. Provider-specific readers receive native identities inside the service boundary and return only canonical IDs and bounded portable fields.

## Runbook compiler

All modes begin with endpoint, permission, release, graph, mapping, fencing and evidence checks.

- `planned_failover`: final synchronization, stop dependants in reverse order, prove source isolation, promote in dependency order, validate, notify and establish reverse protection.
- `unplanned_failover`: record incident reason, prove or explicitly block on source fencing, select recovery evidence, promote in dependency order, validate, notify and establish protection from the active site.
- `failback`: verify reverse protection, final synchronization, stop recovery dependants in reverse order, prove recovery isolation, recover the original site in dependency order, validate and restore original protection direction.
- `test`: create/verify a bubble-network boundary, clone or restore temporary targets in dependency order, run assertions, stop targets and clean up only owned test resources.

Every step has an ID, phase, stage, dependencies, action owner (`docker_dash`, `provider`, or `operator`), mutation flag and required evidence. Plan-level blockers bind missing prerequisites to members where relevant. This slice executes none of the mutating steps.

## Semantic hashing

The plan hash covers schema version, group revision/objectives, endpoint IDs/types, strategy, ordered members/dependencies, canonical mappings, mode, bounded incident declaration, capability state/constraints, stable recovery-evidence IDs and timestamps, measured drill RTO, compliance verdicts, ordered steps, blockers and warnings. It excludes `generatedAt`, continuously changing age-only presentation fields, endpoint secrets, native references and UI formatting. An age crossing an objective changes a warning/compliance verdict and therefore changes the hash.

The run evidence hash covers the plan hash, evaluation state, per-member evidence verdicts, compliance calculation and completion timestamp. Hashes use canonical key ordering and SHA-256.

## Compliance

- `met`: every member has a verified point within RPO and an automated successful restore drill within both RPO/RTO targets;
- `breached`: all required measurements exist, but at least one target is exceeded;
- `failed`: the latest relevant automated rehearsal/drill failed;
- `unknown`: replication, fencing, mapping or measurement evidence is incomplete;
- `never_tested`: no automated successful restore-drill evidence exists for one or more members.

Plan-only rehearsal completion does not change `never_tested` into `met`. Group summary exposes worst-member state and the exact counts behind it.

## Provider capability boundary

The catalog adds `replication.read`, `replication.configure`, `dr.failover`, `dr.failback` and `dr.test`. Proxmox can advertise conditional read-only storage-replication inventory. Mutation capabilities remain unsupported because PVE storage replication alone does not own fencing, network cutover or cross-site recovery. vSphere requires a separate Live Recovery/SRM management boundary. Xen/XAPI requires a discovered, task-backed XO/XAPI recovery workflow. Raw Xen remains unsupported.

## Failure semantics

- provider inventory failure returns typed, sanitized evidence and never a partial `supported` state;
- stale/missing identities block the affected member;
- a database write failure cannot leave a partial group because group/member replacement is transactional;
- a rehearsal is immutable after completion;
- real-mode submission always fails before persistence while mutation capability is unavailable;
- group deletion soft-deletes definitions and never removes immutable completed rehearsal evidence.
