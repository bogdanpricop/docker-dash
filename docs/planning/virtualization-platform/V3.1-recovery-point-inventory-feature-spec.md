# V3.1 — Recovery-point inventory feature specification

**Status:** implemented, repository/CI-validated and deployed to staging
**Release gate:** `DD_PROVIDER_RECOVERY_POINT_INVENTORY=false` by default
**Primary backlog outcome:** B128
**Evidence-only facets:** B136–B138, without policy mutation or verification execution
**Scope:** read-only Proxmox VE/PBS and Xen Orchestra backup inventory; no snapshot, backup, restore, prune, protection or verification action

## Outcome

An endpoint viewer can inspect a provider-neutral list of backup repositories and recovery points, search it, filter by verification state, and see evidence coverage without receiving provider URLs, credentials or archive references. The contract distinguishes missing evidence from failure and labels unmapped/orphaned workloads explicitly.

Snapshots remain a separate V1.3 domain. Neither a hypervisor snapshot nor a provider task is admitted as a recovery point unless it appears in a provider backup repository/archive inventory.

## Public contract

`GET /api/providers/:hostId/recovery-points` accepts:

- `limit` — integer 1–500, default 200;
- `q` — at most 120 characters;
- `repository` — canonical `ddr_repo_*` identity;
- `workload` — canonical `ddr_vm_*` identity;
- `verification` — `verified`, `failed`, `stale`, `unverified` or `unknown`;
- `from` and `to` — an ordered ISO-8601 range.

Schema `1.0` returns provider/observation metadata, filters, coverage counters, repository summaries, limitations and at most the requested number of recovery points. Repository IDs use `ddr_repo_<hash>` and recovery points use `ddr_rp_<hash>`. Native repository/archive/workload references are hashed for lookup and encrypted at rest. Public objects contain canonical IDs and bounded display metadata only.

## Evidence semantics

- `verified` is emitted only for an explicit provider success state;
- `failed` is emitted only for an explicit provider failure/corruption state;
- `unverified` requires explicit “never/none/unverified” evidence;
- `stale` requires an explicit provider state in V3.1;
- absence, unfamiliar shapes and unsupported fields are `unknown`;
- protection and encryption are tri-state booleans; a repository capability is not proof that a recovery point used it;
- application/filesystem consistency stays `unknown` unless a future provider contract proves it.

## Provider matrix

| Provider plane | Inventory source | V3.1 result |
|---|---|---|
| Proxmox VE + PBS | node storage inventory and `content=backup` | repositories and de-duplicated PBS/local recovery points; explicit protection/verification fields retained |
| Proxmox VE without PBS | PVE backup-capable storage | full backup artifacts; verification/encryption normally unknown |
| Xen Orchestra | discovered public REST `backup-repositories` and `backup-archives` collections | repository/archive inventory; URLs excluded and health remains unknown without log evidence |
| XenAPI/XCP-ng direct | no portable backup manager collection | typed unsupported |
| raw Xen/libxl | no managed backup catalog | typed unsupported |
| vCenter/standalone ESXi | no backup manager configured in this product boundary | typed unsupported |

XO is enabled only when both modern GET routes appear in its runtime OpenAPI document. Deprecated/internal JSON-RPC backup routes are not used. Proxmox shared storage content is de-duplicated across nodes, while node-local stores retain separate repository identities.

## Security and operational bounds

1. view access is host-scoped; no admin or mutation privilege is required;
2. feature default is off and a disabled route returns typed 404;
3. provider input is bounded to 500 repositories, 5,000 raw points, 64 KiB per normalized record and 2 MiB per response;
4. all provider failures crossing the route are sanitized;
5. XO repository URLs are never requested; PVE repository configuration URLs are never read;
6. native IDs are never returned as identity fields and are encrypted at rest;
7. provider `unknown` never becomes success;
8. no POST/PUT/PATCH/DELETE provider call or UI mutation control exists in this batch.
