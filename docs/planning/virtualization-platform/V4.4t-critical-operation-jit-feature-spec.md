# V4.4t — Critical provider-operation JIT wiring

**Status:** implemented for v8.91.4; rollout remains default-off pending canary

**Market feature:** B169 follow-up

**Release gate:** `DD_PROVIDER_CRITICAL_OPERATION_JIT=false`

## Outcome

This follow-up connects the shipped local-TOTP/four-eyes JIT lifecycle to four
already implemented provider mutations that are available to operators and
have elevated impact:

| Operation | Exact permission |
|---|---|
| forced VM power off/reboot, single or bulk | `provider.vm.power.force` |
| snapshot revert | `provider.vm.snapshot.revert` |
| snapshot delete | `provider.vm.snapshot.delete` |
| VM migration | `provider.vm.migration.execute` |

Normal start, graceful shutdown/reboot, preflight and read-only routes do not
enter this new gate. Existing administrator-only mutations are not broadened.
Global administrators keep their documented explicit bypass.

## Authorization contract

For a non-admin user, the route accepts an organization or provider scope in
`X-Docker-Dash-Privileged-Scope` and a claimed JIT or active break-glass token
in `X-Docker-Dash-Privileged-Grant`. A JIT token must match all of:

- authenticated user;
- provider endpoint;
- selected scope;
- exact operation permission;
- active, claimed and unexpired state.

The scope predicate is part of the SQLite token lookup. This also closes the
previous gap where the service contract described scope binding but direct JIT
validation did not include `scope_id` in its query. Break-glass remains bound
to user, endpoint, scope and expiry and intentionally spans the critical
permissions inside its approved emergency envelope.

Resource/project scopes are rejected until provider resources have a complete
governance-scope association. Accepting only organization/provider scopes
prevents a narrow-looking project token from authorizing an endpoint-wide
resource accidentally.

## API and UI behavior

When enforcement is enabled and authorization is missing, the API returns
`CRITICAL_OPERATION_JIT_REQUIRED` with operation, permission and safe scope
metadata. The VM page opens one authorization modal and retries the same
mutation with the same idempotency key. Cancellation starts no operation.

The raw grant is never added to the JSON operation body, persisted, or copied
into audit details. Authorization and denial audits retain only operation,
permission, mode, scope, grant/request identifier, expiry and error code.

## Persistence and rollout

Migration 170 adds only the four governance permission rows. No raw-token or
authorization-session table is added. Existing JIT and break-glass tables keep
hash-only token storage.

`DD_PROVIDER_CRITICAL_OPERATION_JIT` is independent of
`DD_PROVIDER_PRIVILEGED_COMPLIANCE`. It stays false by default so deploying the
code cannot strand existing operators. Enabling it requires the base control
plane, configured scopes/roles, enrolled TOTP, an independent approver and a
safe provider canary. B169 remains `Partial` until that rollout evidence plus
browser smoke and SSO/WebAuthn step-up exist.

## Verification

- migration seeds four exact permissions while preserving B176's historical
  ten-permission qualification proof;
- service tests cover exact permission, user, endpoint and scope binding,
  admin bypass and hash-only token storage;
- route tests prove denied calls start no provider mutation, accepted headers
  are not audited raw, and normal power actions bypass the critical gate;
- UI/source tests cover all four retry paths, protected headers and stable
  idempotency keys;
- full Jest, ESLint, registry, i18n, accessibility, syntax and whitespace gates
  run before tag and rollout.
