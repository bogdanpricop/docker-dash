# V4.4f — Network reachability simulation

**Backlog:** B119
**Status:** local simulation-only implementation complete; active probes, browser/provider adapters and release pending
**Scope:** safe control-plane prediction from normalized evidence

## Outcome

Administrators can assess a bounded source/destination/protocol/port tuple from
fresh route, policy, attachment, DNS and optional provider-simulation evidence.
The service persists an immutable `pass`, `fail` or `unknown` result while making
zero network calls and zero provider mutations.

`pass` means **predicted reachable from the supplied control-plane evidence**.
It is never presented as proof that a packet reached the destination or that an
application completed a connection.

## Evidence contract

- The source has a canonical resource key, literal IP address and optional
  network key.
- The destination has a canonical resource key, exactly one literal IP or FQDN,
  and an optional network key.
- Protocol is explicit: TCP, UDP, ICMP or ICMPv6. TCP/UDP require port 1–65535;
  ICMP/ICMPv6 require port 0 and a matching source address family.
- Route, effective policy, source attachment and provider-native simulation are
  individually timestamped and SHA-256 evidence-bound.
- Evidence older than the requested freshness window becomes `unknown`.
- Current normalized DNS observations may resolve a hostname and verify its
  canonical resource. No DNS query is started by this feature.
- Retained normalized flow logs may corroborate the exact five-tuple. Historical
  allow traffic never upgrades otherwise insufficient evidence to `pass`.

## Verdict

- `fail`: an explicit route failure, policy deny, absent source attachment,
  provider-simulation deny, DNS identity conflict or IP-family conflict exists.
- `pass`: the attachment and destination identity are known and either a fresh
  provider simulation allows the tuple or both route and policy allow it.
- `unknown`: required evidence is missing, stale or inconclusive.

Every result includes interpretation, confidence, failure codes, signal
freshness, DNS state, flow corroboration and the active-probe boundary.

## Persistence, API and UI

- Migration 164 stores simulation-only assessments with database checks fixing
  network-call and provider-mutation counters to zero.
- Assessments are SHA-256 deduplicated over canonical input, derived evidence and
  verdict.
- The admin-only audited Network Advanced endpoint accepts normalized JSON.
- Network Advanced shows endpoints, tuple, verdict, confidence, signal states,
  flow state and immutable hash.
- Exact input schemas reject arbitrary fields and secret-shaped material.

## Active-probe boundary

This slice intentionally exposes no probe or execute endpoint. Before active
TCP/UDP/ICMP checks can be implemented, the product needs an approved runner
identity and network zone, verified source ownership, a destination allowlist or
policy, per-tenant rate limits, timeouts, egress controls and an audit model.
Arbitrary shell and user-supplied commands remain prohibited.

## Acceptance evidence

- fresh simulated route/policy/attachment pass without network traffic;
- explicit deny produces fail;
- stale or incomplete evidence produces unknown;
- hostname correlation uses retained normalized DNS evidence;
- exact five-tuple history is visible but non-authoritative;
- deterministic dedupe, secret rejection, RBAC and database safety checks;
- audited API, UI boundary, focused tests, lint and registry reconciliation.
