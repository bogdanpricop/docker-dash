Each backup used the running application's online `better-sqlite3` backup API,
was copied outside the volume and set to mode 0600. The exact database file was
then mounted beneath a writable `/backup` tmpfs into the previous production
image with root filesystem read-only, user `0:0`, no network and a separate
bounded `/tmp`; `PRAGMA quick_check` passed on both targets. Release-private env
copies are mode 0600.

The first validation attempts stopped before build because the previous image's
entrypoint tried to write `/data/.env` and then because SQLite had no writable
parent for WAL metadata. No production container was changed. The successful
validation bypassed the entrypoint with `--entrypoint node` and used the direct
file mount under `/backup`; the already verified online backups were reused.

## Deployment and rollback method

Both hosts checksummed and extracted the same Git archive, built the Dockerfile
`production` target with `APP_VERSION=8.63.0`, validated Compose and recreated
only the app:

```sh
APP_VERSION=8.63.0-61c46c3 docker compose \
  --project-directory "$BASE" --env-file "$BASE/.env" \
  -f "$RELEASE/docker-compose.yml" up -d --no-build --no-deps app
```

The exact source archives were removed after success. Image and extracted
release `8.62.0-9362b9f` remain on both hosts as the immediate rollback target;
no global Docker cleanup was run.
