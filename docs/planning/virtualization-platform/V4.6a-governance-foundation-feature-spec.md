# V4.6a — Governance foundation

**Release target:** v8.49.0 (2026-07-29)
**Backlog:** B176–B185

## Outcome

Docker Dash adds a scoped governance control plane over the existing tenant
seam. The batch delivers ten connected capabilities:

1. B176 — an explicit permission catalog (`resource.verb`);
2. B177 — custom roles composed only from catalog permissions;
3. B178 — organization/site/provider/cluster/project/resource scope hierarchy;
4. B179 — delegated site administration inherited only by descendants;
5. B180 — project lifecycle, members, owners and assigned resources;
6. B181 — hashed, expiring, single-use project invitations with email/domain gates;
7. B182 — transactional ownership transfer that cannot orphan a project;
8. B183 — CPU soft/hard quota with current usage;
9. B184 — memory soft/hard quota with current usage;
10. B185 — storage soft/hard quota with current usage.

The existing `tenants` and `user_tenants` tables remain authoritative for
project identity and membership. Existing provider resources are not moved or
mutated; `governance_project_resources` is an explicit accounting assignment.

## Scope and anti-scope

In scope: governance API/UI, inherited permission evaluation, users and teams as
subjects, lifecycle `active/suspended`, manual resource accounting, soft quota
warnings, hard quota refusal, audit events and read-only usage summaries.

Out of scope: automatic discovery/claiming of provider resources, billing,
network/snapshot/GPU quotas (B186–B188), quota approvals (B189), retrofitting
every legacy Docker/provider route to the new catalog, and provider mutations.
Existing host/stack RBAC remains enforced independently.

## Data model

Migration `124_governance_foundation.js` adds:

- `governance_permissions`, `governance_roles`, `governance_role_permissions`;
- `governance_scopes`, `governance_role_bindings`;
- `governance_project_resources`, `governance_project_quotas`;
- `governance_project_invitations`.

The migration is additive. It seeds the organization root, built-in safe roles,
the permission catalog and a project scope for every existing tenant. Raw
invitation tokens are never persisted; only SHA-256 digests are stored.

## Authorization and safety

Global Docker Dash admins bypass governance lookup. Other users receive catalog
permissions through direct/team bindings on a scope; permissions inherit only
downward. A delegating user may grant only a role whose permissions are a subset
of their own effective permissions on the target scope. Project membership also
creates/removes the matching built-in project-role binding.

Hard quota checks run in the same SQLite transaction as resource assignment.
Unknown/negative/non-finite accounting values are refused. Soft-limit excess is
returned as a warning and does not silently become a hard failure. The last
owner cannot be removed, and ownership transfer first validates an active target
user before replacing the owner.

## API

All endpoints are authenticated under `/api/governance`. Mutations also pass the
global writable/policy gate and are audited.

- catalog/role/scope/binding inventory and administration;
- accessible project list, create, detail and lifecycle update;
- project member add/remove and ownership transfer;
- invitation create/list/revoke/accept;
- quota read/update and resource assign/unassign.

## Failure and rollback

Invalid hierarchy, privilege escalation, expired/reused invitations, orphaning,
duplicate resource ownership and hard-quota excess fail closed with structured
4xx responses. No provider call occurs. Rollback redeploys the prior image; the
additive tables are ignored by old code and must not be dropped automatically.
