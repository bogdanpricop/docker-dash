# V1.8 Deep spec — console authorization and protocol relay

## Authorization sequence

1. REST preflight resolves the canonical VM identity, live provider capability, power state, host permission and effective lock.
2. Issue creates a random 32-byte base64url token, stores only its SHA-256 hash and binds it to user, provider host and canonical VM.
3. The new window receives the token in a URL fragment. Client code removes the fragment before network activity and supplies it as a dedicated WebSocket subprotocol.
4. Upgrade validates exact path, allowed origin, binary protocol, authenticated session and per-user/per-IP capacity before atomically consuming the token.
5. The gateway rechecks endpoint permission, lock, active provider record and canonical identity before opening the provider transport.
6. A safe bootstrap announces only protocol, provider, display name and maximum duration. Relay starts only after the client acknowledges attachment.
7. Close/error/timeout/lock tears down both channels and records a bounded close code.

## Data model

`provider_console_sessions` contains session ID, token hash, host/VM/user scope, provider/protocol and lifecycle timestamps. It never stores the raw token or an upstream credential. Expired/closed rows are retained briefly for diagnostics and deleted by bounded issue-time cleanup; durable operator evidence remains in the audit log.

`provider_console_access_locks` stores one lock per global, host or canonical VM scope with reason, administrator and timestamp. Effective precedence is environment `deny`, environment recovery `allow`, global, host, VM, managed allow. The default-off feature flag always blocks before the override is evaluated.

## Relay contracts

### RFB

The gateway accepts upstream RFB 3.3/3.7/3.8 and VMware 4.x/5.x banners. VMware extensions are downgraded by selecting 3.8. Security type `None` or classic VNC challenge/response is completed server-side; DES bit order follows the RFB specification and the password is capped to eight Latin-1 bytes. A synthetic RFB 3.8 `None` handshake is then exposed only inside the already authorized WebSocket.

`ByteChannel` reassembles partial stream/WebSocket frames for exact handshake reads, then switches to full-duplex binary forwarding. Reads, headers, messages and connection attempts are bounded. permessage-deflate is disabled.

The general `/ws` endpoint and the console gateway both use explicit `noServer` routing. Each upgrade listener returns without touching paths it does not own, preventing one WebSocket service from rejecting another service's handshake.

### Provider adapters

- Proxmox creates a short VNC proxy ticket and connects to the node-local WebSocket with the API session header. The VNC ticket password never crosses the gateway.
- vSphere logs in, calls `AcquireTicket` with `webmks`, validates a `wss:` endpoint, relays the ticket socket and logs out on teardown.
- Xen Orchestra uses a configured scoped token to connect to its official console proxy.
- XAPI selects RFB before VT100 from `VM.get_consoles`; it attempts WSS and falls back to the documented TLS `CONNECT` request with the XAPI session cookie.
- raw Xen opens a PTY over the existing pinned-host-key SSH boundary and runs only the allowlisted `xl console` or `xm console` command.

## Failure behavior

| Failure | Behavior |
|---|---|
| flag/capability/state/permission/lock blocker | no token issued |
| expired, reused or wrong-user token | HTTP 401 upgrade rejection |
| capacity exceeded | HTTP 429 without consuming a new token |
| permission revoked after issue | token closed and upgrade rejected |
| upstream ticket/handshake failure | safe client error, audit failure and channel teardown |
| emergency lock | matching sockets close with code 4003 locally and through cluster pub/sub |
| maximum duration | normal close and provider transport teardown |

## Compatibility and rollout

Migration 113 is additive. Existing provider APIs are unchanged and the feature flag defaults to false. Rollout enables one provider endpoint at a time after live console validation. Recovery can set `DD_PROVIDER_VM_CONSOLE_ACCESS_OVERRIDE=deny` and restart, or apply a database lock without restart.
