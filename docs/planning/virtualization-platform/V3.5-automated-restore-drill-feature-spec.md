# V3.5 — Automated restore drill feature specification

**Status:** implemented, validated, and deployed to staging

**Release gate:** `DD_PROVIDER_RESTORE_DRILLS=false` by default

**Executable scope:** Proxmox VE QEMU and LXC recovery points restored into a new temporary VMID

## Outcome

V3.5 proves more than archive integrity. It creates a new restore target through the V3.4 safety boundary, disconnects every restored NIC before boot, starts the temporary workload, records bounded boot and guest-agent assertions, stops it, and deletes it only after exact ownership and cleanup checks. Failed drills preserve their stopped target by default for forensic inspection.

The first executable slice is Proxmox VE. Xen Orchestra's product health checks are the behavioral reference, but XO remains fail-closed until Docker Dash has a conformance-tested mutation/task transport. vSphere, ESXi, raw Xen, and XAPI are also capability-blocked.

## User stories

1. An administrator can preflight a drill from a canonical recovery point and see target, isolation, assertion, cleanup, RPO, RTO, and capability evidence without mutation.
2. A submitted drill is one durable `recovery.drill` operation and one durable drill run with an evidence hash.
3. The restored target cannot boot until every configured NIC reports `link_down=1` and an exact operation marker is present.
4. QEMU drills can require guest-agent ping and bounded OS evidence; LXC drills report boot-only evidence rather than inventing an agent signal.
5. Successful drills can delete only the exact stopped, marked, newly restored target after a second typed cleanup confirmation.
6. Failed, cancelled, ambiguous, unmarked, or unexpectedly running targets are never automatically deleted.
7. A backup policy can schedule sampled drills in an IANA timezone, deduplicated by due slot.
8. Operators can list drill history with RPO age, RTO duration, assertions, cleanup result, and tamper-evident evidence hash.

## Assertions and cleanup

- `boot`: mandatory; provider inventory must report the exact isolated target running before timeout;
- `guestAgent`: `required`, `optional`, or `disabled`; QEMU only, using the bounded PVE agent ping and OS-info endpoints;
- arbitrary guest commands, credentials, HTTP callbacks, and scripts are not accepted in this batch;
- cleanup modes are `on_success` and `never`; failures are retained stopped;
- cleanup requires `allowAutomaticCleanup=true` and exact `DRILL DELETE <vmid>` confirmation;
- force-stop fallback applies only to the marked temporary target and must be explicitly visible in the plan;
- destroy uses `purge=false` and `destroy-unreferenced-disks=false`, then verifies target absence.

## Acceptance criteria

- additive migration stores policies/runs without provider-native references or secrets;
- a separate feature flag and `backup.restore.drill` capability default fail-closed;
- preflight composes V3.4 live restore checks and adds drill-specific isolation/assertion/cleanup gates;
- plan hash includes every destructive or timing choice and excludes volatile presentation fields;
- restore/start/stop/destroy have durable pre-submit checkpoints and no unsafe replay after ambiguity;
- all NICs and the exact drill marker are re-read before start and again before delete;
- success requires restore task, stopped target, isolation, boot, requested assertions, stop, and requested cleanup evidence;
- failure/cancel never deletes a target and returns manual-inspection evidence;
- due-slot scheduling is leader-gated, idempotent, and samples a verified point from the linked backup policy;
- RPO/RTO outcomes and a SHA-256 evidence hash are queryable without decrypting operation requests;
- route RBAC, sanitized errors, canonical audit, client, state-machine, scheduler, UI, migration, full-suite, lint, CI, staging, database, HTTP, and rollback checks pass.

## Primary sources

- Proxmox Backup Server recommends frequently restoring and booting backups into a new guest, and automating or sampling those tests: <https://pbs.proxmox.com/docs/storage.html#ransomware-protection-recovery>.
- Proxmox VE QEMU/LXC network schemas define `link_down` as disconnecting an interface like pulling the plug: <https://pve.proxmox.com/pve-docs/qm.1.html> and <https://pve.proxmox.com/pve-docs/pct.1.html>.
- Proxmox `qemu-server` exposes task-backed start/stop/destroy and bounded guest-agent ping/OS information with `VM.GuestAgent.Audit`: <https://git.proxmox.com/?p=qemu-server.git>.
- Proxmox `pve-container` exposes task-backed start/stop/destroy and the same `link_down` configuration property: <https://git.proxmox.com/?p=pve-container.git>.
- Xen Orchestra health checks restore, boot, wait for guest tools or a constrained xenstore assertion, and delete the restored VM within a ten-minute envelope: <https://docs.xen-orchestra.com/backups#backup-health-check>.
