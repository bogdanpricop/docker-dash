# V0.4 Deep spec — Provider conformance kit

## Contracte

### Manifest `1.0`

```json
{
  "schemaVersion": "1.0",
  "providerType": "xen",
  "displayName": "Xen",
  "owner": { "service": "virtualization", "team": "platform", "runbook": "/docs/features/provider-conformance" },
  "variants": [{ "id": "xapi", "apiFamilies": ["XAPI JSON-RPC", "XAPI XML-RPC"], "releaseRing": "beta" }],
  "compatibility": [{ "variant": "xapi", "status": "contract-tested", "evidence": "fixture:xen-xapi" }],
  "mutationRequirements": { "idempotency": true, "locking": true, "reconciliation": true, "postValidation": true, "canary": true, "waves": true },
  "deprecations": []
}
```

Valorile `releaseRing` sunt `internal`, `canary`, `beta`, `ga`. Compatibility status este `declared`, `fixture-tested`, `endpoint-tested` sau `deprecated`; doar un run live poate produce evidence `endpoint-tested`.

### Run `1.0`

- mode: `static` sau `live_readonly`;
- state: `running`, `passed`, `warning`, `failed`;
- grade: `certified`, `conditional`, `failed`;
- checks: `passed`, `warning`, `failed`, `skipped`, fiecare cu categorie, weight, durată și evidence sanitizat;
- `evidenceHash`: SHA-256 peste manifest hash, identitatea endpoint-ului, mode și checks canonice; timestamps volatile nu intră în hash.

## Runner static

Checks obligatorii:

1. adapter type și metode minime;
2. validitatea manifestului și potrivirea tipului;
3. catalog complet de capabilities și evidence valid;
4. mapping capability inventory → `listResources`;
5. fixture corpus valid și fără secrete;
6. failure taxonomy disponibilă;
7. release/deprecation metadata;
8. operation safety declarations pentru capabilități mutabile.

Runner-ul acceptă adapter și fixtures injectate, astfel încât pluginurile viitoare să folosească exact același kit.

## Live read-only

1. capability probe cu refresh și limită de timp;
2. validarea envelope-ului;
3. pentru fiecare inventory declarat supported/conditional: cel mult 25 resurse;
4. validarea schemelor și a ID-urilor stabile prin două citiri ale primului eșantion;
5. leak scan peste rezultatul serializat;
6. latență și status pentru scorecard/SLO baseline.

Nu se apelează nicio metodă mutation. Dacă endpoint-ul este indisponibil, run-ul rămâne evidence valid dar grade `failed`.

## Resilience

- stare circuit per `hostId`; prag implicit 3 erori tranzitorii;
- open cooldown implicit 30 secunde;
- un singur apel half-open;
- coadă bounded și concurrency inițial 2 per endpoint;
- rate-limit/auth/transport reduc bugetul; succese consecutive îl cresc lent până la maximum;
- timeout implicit 30 secunde; rezultatele târzii nu schimbă run-ul finalizat.

## DB migration 108

- `provider_conformance_runs`: run metadata, score/grade, hashes și timestamps;
- `provider_conformance_checks`: checks ordonate și evidence JSON sanitizat;
- index host/time și provider/time;
- FK host/user cu `SET NULL`, checks cu `CASCADE`.

## API și RBAC

- `GET /api/providers/manifests`: autentificat;
- `GET /api/providers/scorecard`: autentificat;
- `GET /api/providers/:hostId/conformance`: view access pe host;
- `GET /api/providers/:hostId/conformance/:runId`: view access pe host;
- `POST /api/providers/:hostId/conformance`: admin + host view; singurul mode public este `live_readonly`.

Audit event: `provider_conformance_run`, fără payload provider și fără credentiale.

## Failure modes

- circuit open: 503 `PROVIDER_CIRCUIT_OPEN`;
- budget queue full: 429 `PROVIDER_BUDGET_EXHAUSTED`;
- timeout: 504 `PROVIDER_REQUEST_TIMEOUT`;
- contract/fixture invalid: check failed, fără crash al procesului;
- DB write eșuat: run eșuează fail-closed și nu este prezentat ca certified;
- leak detectat: check failed și evidence înlocuit cu marker redacted.

## Rollback

Migrarea este aditivă. V0.3 ignoră tabelele 108. Revenirea la imaginea anterioară păstrează run-urile pentru o reinstalare ulterioară; nu se șterg automat.
