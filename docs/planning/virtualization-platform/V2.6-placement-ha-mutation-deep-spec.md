# V2.6 — Placement and HA mutation deep specification

## Architecture

```text
portable request
  -> bounded input validation
  -> endpoint capability + operation policy
  -> live provider snapshot
  -> semantic diff + stable hash + expiry
  -> encrypted pending approval request
  -> independent administrator approval
  -> full live re-plan / stale rejection
  -> durable placement.change operation
       policy: native incremental mutation -> task reconcile -> live post-read
       rebalance: persisted waves -> V2.2 child migration -> placement post-read
  -> append-only change and global audit events
```

## Hash and expiry

The semantic hash includes endpoint, change kind, portable resource identities, normalized before/desired state, diff, provider capability evidence, and rebalance moves. It excludes timestamps, display-only text, transient task references, and actor identity. The stored `expires_at` limits approval, while the hash remains deterministic during the window.

## Approval transaction

Approval is one database transaction after a successful live re-plan:

1. compare request state and expiry;
2. assert `requested_by != approving_user`;
3. compare stored and recomputed semantic hash;
4. update state and approval fields with a compare-and-set;
5. create the durable operation with a deterministic idempotency key;
6. attach the operation ID and append an event.

If operation creation fails, the transaction is rolled back. Repeated approval returns the existing operation to the same authorized approver and cannot create a second mutation.

## Provider translators

### Proxmox

- resolve canonical VM IDs to `qemu/<vmid>` or `lxc/<vmid>` and emit HA resource IDs as `vm:<vmid>`/`ct:<vmid>`;
- use `/cluster/ha/resources` for resource policy and `/cluster/ha/rules` for PVE 9+ affinity rules;
- create/update/delete by stable rule key;
- immediately re-read resources/rules because these API calls do not expose a durable cluster task;
- rollback builds a fresh inverse from the observed row, never from a serialized REST payload.

### vSphere

- require vCenter and a canonical `ClusterComputeResource` scope;
- send `ClusterConfigSpecEx` with `modify=true` and exactly one `dasVmConfigSpec` or `rulesSpec` delta;
- require `Host.Inventory.EditCluster` at the provider;
- bind the returned Task MoRef, reconcile `Task.info.state`, then re-read `configurationEx`;
- V2.6 rule writes accept only VM-VM rules. VM-host group creation/edit/delete is not silently emulated.

### Xen XAPI

- use `VM.set_ha_restart_priority`, `VM.set_order`, and `VM.set_start_delay` only for fields advertised by live discovery;
- create/destroy `VM_group` and update membership with `VM.set_groups`;
- use `VM.set_affinity` for one-VM home-server preferences;
- synchronous calls are post-read verified; a lost response becomes unknown unless the desired state is subsequently observed;
- preserve unrelated group membership and reject inputs that exceed the one-group server constraint.

## Rebalance state machine

```text
pending_approval -> approved -> applying -> verifying -> succeeded
                                 |   ^
                                 v   |
                               paused
                                 |
                           cancelled/failed/unknown
```

Each worker pass reconciles submitted child operations before dispatching. It fills at most `waveSize - submittedCount` slots. A child is created only after V2.2 preflight proves the approved source, target, mode, power state, compatibility, capacity, policy, locks, and stable identities. Source drift to the already-approved target is reconciled as success; any other drift pauses.

`pause` stops new dispatch and leaves submitted migrations reconciling. `cancel` requests cancellation of submitted operations and marks only undispatched items cancelled. `resume` requires every failed/cancelled/unknown child to have an explicit resolved outcome or a new live preflight. Maintenance windows are checked before each dispatch. Stop conditions are: first failed/unknown child, plan drift, target ceiling breach, provider emergency/read-only/freeze policy, or window close.

## Semantic rollback

For HA and affinity mutations, rollback planning reads current state, sets desired state to the original captured before-state, and returns a new diff/hash/expiry. For a created rule, rollback means delete only if the current rule still semantically matches what V2.6 created. For a deleted rule, rollback means recreate under the same name only if that name is free.

For rebalance, rollback planning reverses only succeeded moves whose VM is still on the V2.6 target. Every reverse move receives a fresh migration preflight; non-reversible items are blockers. The result is another `rebalance_apply` request and is never auto-approved.

## Failure semantics

| Failure | State/control |
|---|---|
| stale plan at request or approval | HTTP 409, no mutation |
| approval race | one CAS winner; later request returns existing result |
| provider validation fault before submit | `failed` |
| lost transport after synchronous submit | live read; otherwise `unknown` |
| durable native task pending | `applying`, reconciled without replay |
| native task fault | `failed`, provider detail bounded/redacted |
| post-read mismatch | `unknown` |
| child migration failure/unknown | rebalance `paused` |
| process restart | leases expire; parent and children reconcile from DB |
| operation policy changes mid-run | no new child dispatch; `paused` |
