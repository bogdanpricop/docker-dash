# V3.7 — Restore and replication depth control plane

**Status:** implemented locally, provider mutations fail-closed

**Market features:** B139–B148

**Release gate:** `DD_PROVIDER_RESTORE_REPLICATION_DEPTH=false`

## Outcome

This increment joins the existing automated restore-drill scheduler and DR
runbooks with the missing advanced recovery contracts:

- a bounded, searchable file-catalog evidence store;
- file download/restore, instant, differential and cross-site copy preflights;
- draft async, near-sync and sync replication policies with explicit RPO,
  schedule, bandwidth and storage mapping;
- the existing protection-group dependency graph and planned/unplanned
  failover, test and failback rehearsal compiler.

It does not claim a provider transfer or mutation that the selected adapter
cannot prove. Every advanced restore plan is persisted with canonical IDs,
capability evidence, safety constraints, an expiry and a deterministic SHA-256
hash. It remains blocked by `EXECUTION_ADAPTER_UNAVAILABLE` in this release.

## Contracts

### File catalog

`provider_recovery_file_catalogs` binds one current manifest to a canonical
recovery point. `provider_recovery_file_entries` retains metadata only:
absolute POSIX path, parent, type, size, modified time, optional checksum and
bounded non-secret flags. Backslashes, control characters, traversal segments,
duplicates and oversized batches are rejected. Backup file bytes and native
provider references are never persisted or served.

### Advanced restore plans

`provider_restore_depth_plans` supports:

| Kind | Required evidence | Mandatory safety |
|---|---|---|
| `file_download` | file catalog + provider file capability | metadata-only plan; no content endpoint |
| `file_restore` | catalog paths + destination root | overwrite is always false |
| `instant` | provider instant-restore capability | isolated network |
| `differential` | canonical base recovery point + base checksum | isolated target |
| `cross_site_copy` | distinct target endpoint | resumability, checksum verification and bandwidth ceiling |

All five modes are plan-only until a conformance-tested task identity,
reconciliation strategy and post-read verification exist.

### Replication policies

`provider_replication_policies` stores canonical source/target endpoint IDs,
canonical workload and storage IDs, mode, RPO, schedule, bandwidth, capability
evidence, revision and policy hash. Sync RPO is capped at 60 seconds and
near-sync at 300 seconds. Draft creation/update/delete is audited. `enabled:true`
is rejected even if a provider reports a conditional capability; enabling
requires a future dedicated executor and rollout gate.

## Security, RBAC and audit

- viewers may read catalogs and draft policies for endpoints they can view;
- admins with endpoint operate permission may import evidence and author plans;
- write mode is required for catalog import, plan persistence and policy edits;
- UI renders provider/catalog data through HTML escaping;
- audit details include canonical IDs and evidence hashes, never file content,
  credentials or native provider references;
- deletion is soft for replication policies and never deletes provider data.

## Existing B139–B140 and B146–B148 coverage

Automated isolated Proxmox restore drills, the cron scheduler, success-only
cleanup ownership, protection groups, deterministic failover/failback plans,
RPO/RTO evidence and immutable rehearsals remain implemented by V3.5 and V3.6.
Real failover/failback stays blocked until provider fencing, isolated networking,
durable tasks, data-authority reversal and reprotection are implemented.
