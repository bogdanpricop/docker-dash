# V4.2a — Storage posture assumption audit

| Assumption | Counterexample | Contract decision |
|---|---|---|
| missing storage accessibility means inaccessible | some APIs omit the field for a healthy backend | represent `unknown`, never fail or pass by default |
| a capacity percentage reserves storage | concurrent allocations and thin provisioning can consume space after read | posture is advisory only; mutations must revalidate separately |
| physical free bytes prove thin-provisioning safety | virtual allocation can exceed physical capacity | display a separate overcommit warning when both values exist |
| datastore/SR type proves QoS or multipath health | type is topology metadata, not path/latency telemetry | QoS and multipath remain unknown until native adapters exist |
| maintenance has one provider spelling | vSphere and other APIs use different values or omit a normal state | normalize only recognized values; preserve unknown otherwise |
| an unavailable provider implies unhealthy storage | a network/credential issue prevents an observation | return provider-unreachable error, not a storage-health result |
| provider-native storage IDs are safe to expose | references can disclose topology and enable confused-deputy requests | emit only canonical identity-store IDs |
| a read-only page needs no access check | storage layout/capacity is sensitive operational information | require host `view` access |

## Audit probes

1. Prove inaccessible and >=95% storage produce `fail` signals.
2. Prove 85–<95% usage and virtual allocation over capacity produce warnings.
3. Prove missing QoS/multipath evidence remains `unknown`, never `pass`.
4. Prove only an adapter that advertises `storage.health.read` can serve the endpoint.
5. Prove route errors do not expose upstream detail or native identifiers.
6. Prove a Proxmox storage row without active/status evidence normalizes accessibility to null, not false.
