# V3.5 — Automated restore drill deep specification

## 1. Safety invariants

1. The source workload and recovery point are read-only inputs.
2. The destination VMID must not exist at preflight or execution time.
3. Restore always uses `force=0`, `unique=1`, `start=0`, and no live restore.
4. Start is forbidden until the exact target config has a Docker Dash drill marker and every `netN` contains `link_down=1`.
5. No assertion may reconnect a NIC or execute an arbitrary guest command.
6. Stop applies only to the exact marked target created by this run.
7. Delete applies only after a live stopped-state and marker re-read; ambiguous ownership is permanent manual evidence.
8. Failure and cancellation never authorize delete. `on_success` cleanup is the only automatic deletion mode.
9. Every non-idempotent provider boundary has an encrypted durable checkpoint before submission.
10. Provider-native archive, node, storage, and UPID references never enter public run/audit payloads.

## 2. Durable model

`provider_restore_drill_policies` stores a backup-policy link, IANA schedule, canonical target node/storage, assertion policy, cleanup policy, and RPO/RTO targets. `provider_restore_drill_runs` stores canonical source/target IDs, the operation link, due slot, state, bounded evidence, RPO/RTO measurements, and evidence hash.

Run IDs use `pdrr_<26 hex>` and schedule IDs use `pdrp_<26 hex>`. A unique `(policy_id, slot_key)` constraint prevents duplicate scheduled drills. Operation engine locks cover the recovery point, target VMID, target node, and target storage.

## 3. Operation state machine

```text
restore-submit -> restore-native/discovery -> stopped target
  -> isolation-submit -> isolation-verify
  -> start-submit -> start-native/discovery -> running
  -> boot assertion -> guest-agent assertion (optional/required)
  -> shutdown-submit -> shutdown-native/discovery
  -> force-stop only after bounded timeout on the marked target
  -> stopped
  -> destroy-submit -> destroy-native/discovery (success cleanup only)
  -> terminal evidence
```

The encrypted native-task checkpoint contains schema version, stage, node, VMID, guest type, current UPID when present, bounded timestamps, assertion outcomes, and intended terminal outcome. Its parser rejects unknown stages, invalid IDs, oversized fields, or provider mismatch.

### Ambiguity rules

- interrupted restore submission searches for the exact new target and never resubmits restore;
- interrupted start/stop/destroy submission reconciles provider state and never guesses ownership;
- a missing task plus contradictory workload state becomes `unknown` and retains locks;
- native task failure returns `failed` with partial-target evidence;
- an unmarked target, reconnected NIC, changed node/type/VMID, or unexpected running state blocks cleanup permanently.

## 4. Assertions

The mandatory boot assertion requires live inventory state `running` for the exact node/type/VMID. QEMU guest-agent ping uses only the official `agent/ping` endpoint; optional OS evidence is reduced to bounded `name`, `version`, `kernel-release`, and `machine` strings. LXC reports guest-agent assertion as unsupported and can execute only when the policy chooses `disabled`.

Application-specific scripts are deliberately deferred. A future contract needs named, pre-registered assertions, immutable definitions, output limits, timeout/resource controls, secret references, and an approval boundary; accepting arbitrary commands in a restore workflow would be remote-code-execution by design.

## 5. Scheduling and sampling

Schedules reuse the backup-policy frequency model: hourly/daily/weekly/monthly, quarter-hour minute, IANA timezone, weekday, and day-of-month. The leader cron wakes once per minute. For each due slot it:

1. proves the linked backup policy and endpoint are active;
2. refreshes current backup-policy scope and recovery inventory;
3. selects the newest verified recovery point from the current scope, preferring a workload with the oldest successful drill;
4. allocates the current PVE next VMID;
5. runs live preflight and persists either a blocked run or one operation;
6. deduplicates through both due-slot uniqueness and operation idempotency.

## 6. Evidence and compliance

RPO age is the number of seconds between recovery-point creation and run creation. RTO is measured from operation start to assertion completion, with cleanup duration reported separately. The public evidence contains only canonical IDs, state transitions, assertion booleans/timestamps, cleanup outcome, error codes, and duration metrics.

`evidence_hash = SHA256(canonical(run identity + plan hash + state + measurements + evidence))`.

The compliance projection distinguishes:

- `met`: a successful drill with RPO and RTO at or under target;
- `breached`: a successful drill exceeding either target;
- `failed`: restore/assertion failure;
- `unknown`: incomplete or ambiguous evidence;
- `never_tested`: no terminal run.

## 7. Cancellation and rollback

Cancellation attempts to stop an active native task and stop a running marked target, but returns `unknown` until the final provider state is proven. It never deletes. Database migration 120 is additive and old application code ignores the new tables. Deployment rollback uses the prior immutable image; run evidence remains forward-readable.
