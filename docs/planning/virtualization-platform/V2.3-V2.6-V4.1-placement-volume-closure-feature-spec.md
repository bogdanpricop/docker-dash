shipped host-maintenance, placement-change and managed-volume implementations.

evidence-bound recovery dependency DAG rather than only descriptive priority
groups.

## Recovery DAG contract

- Only protected, powered-on workloads participate; excluded workload count is
  explicit.
- Explicit dependency references are converted to canonical resource IDs.
  The latest B019 relationship graph supplies `depends_on`, `requires`,
  `starts_after` or reverse `required_by` edges when both endpoints belong to
  the HA domain. Provider-native references never leave the service.
- Optional B017 integer metadata keys `recovery.ready_seconds`,
  `recovery.start_order` and `recovery.start_delay_seconds` enrich timing
  without introducing a parallel configuration store.
- Explicit dependencies take precedence. Xen/XAPI `order` and `start_delay`
  provide the next fallback; provider restart-priority groups are advisory-only.
- Cycles, self-dependencies and references outside the recoverable set produce
  `blocked`, not a guessed schedule.
- A wave receives a start or ready time only when its prerequisite and duration
  evidence is complete. Unknown timing stays `null` and is rendered as
  “evidence unavailable”.
- The visualizer presents ordered waves, workload nodes, dependency evidence,
  confidence, blockers and estimated completion. It does not start VMs or
  change provider HA state.

## Safety and compatibility

The recovery fields are additive to the encrypted HA readiness snapshot. No
database migration or feature-flag change is required. Existing cached
snapshots remain readable and display the prior priority view until refreshed.
All mutation capabilities remain behind their existing independent release
flags and approval/idempotency controls.
