# V4.6b — Identity and policy governance

**Release target:** v8.50.0 (2026-07-29)
**Backlog:** B186–B195

## Outcome

V4.6b extends the scoped governance foundation with ten connected controls:

1. B186 — explicit NIC, network, public-IP and security-group quotas;
2. B187 — snapshot/backup count and byte quotas;
3. B188 — GPU, device and accelerator-time quotas with optional profiles;
4. B189 — audited, time-bound quota-increase requests;
5. B190 — multi-realm OIDC/SAML-broker discovery and email-domain routing;
6. B191 — SCIM 2.0 user/group lifecycle provisioning;
7. B192 — hashed, scoped, short-lived service tokens with rotation/last-used;
8. B193 — JWT workload identity exchange for OIDC/SPIFFE/cloud issuers;
9. B194 — hash-bound one/two-person policy approvals;
10. B195 — mutation blackout windows with recorded emergency exceptions.

## Boundaries

Extended quota usage is explicit control-plane accounting. It does not scan,
reserve, attach, detach or mutate provider resources. Snapshot/backup byte
accounting accepts evidence supplied by an authorized caller; automatic provider
discovery remains separate.

Federation realms route an email domain to a configured login handoff. The
existing native OIDC flow can be selected directly; multiple OIDC or SAML realms
can hand off to a trusted identity broker. Docker Dash does not accept unsigned
SAML assertions or implement an ad-hoc XML signature stack.

SCIM endpoints require a short-lived service token carrying `scim.read` or
`scim.write`. SCIM deletion deactivates users and invalidates sessions; it does
not erase audit history. Workload exchange accepts signed JWT assertions only,
using an administrator-pinned JWK set. Symmetric/`none` algorithms, expired or
overlong assertions, issuer/audience/subject mismatch and replay are rejected.

## Authorization and approval

Service tokens are returned once, stored only as SHA-256 hashes, expire within
24 hours (workload tokens within one hour), have a fixed scope catalog and can
be rotated or revoked. They are denied outside their explicit API scope.

Approval requests bind method, normalized path and canonical payload hash.
Approvers must be distinct and, when configured, cannot be the requester.
Approved requests are atomically claimed before execution and become consumed
only after a successful HTTP response.

Blackout windows match action path, environment and optional governance scope.
Mutations fail with HTTP 423 while active. An exception requires a global admin,
an explicit emergency reason and ticket, and a window that permits emergency
override; every accepted exception is persisted.

## Data and rollback

Migration `125_governance_identity_policy.js` is additive. It adds extended
quota/allocation, quota request/grant, approval, identity realm, service-token,
SCIM mapping, workload trust/replay and blackout/exception tables. It also adds
catalog permissions without weakening existing roles.

Rollback redeploys v8.49.0. Old code ignores the additive tables. Database
tables are never dropped automatically; a verified pre-release backup is the
only data-rollback source.

## Verification

- quota soft/hard enforcement and time-bound grant expiry;
- one/two-person approval, payload binding and single-use claim;
- blackout matching and emergency exception audit;
- service-token expiry, scope enforcement, rotation and last-used;
- SCIM user/group lifecycle and session invalidation;
- RS256/ES256/EdDSA workload assertion verification and replay denial;
- public realm routing without exposing configuration secrets;
- full Jest, ESLint, syntax, production image and dual-target rollout checks.
