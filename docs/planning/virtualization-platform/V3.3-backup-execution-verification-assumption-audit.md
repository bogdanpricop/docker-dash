| Assumption | Evidence / treatment | Status |
|---|---|---|
| Enabling policy planning authorizes backup mutation | Independent release flag and per-policy execution authorization | rejected |
| A saved plan remains safe to execute later | Full live preflight and exact hash comparison immediately before persistence | rejected |
| Inventory timestamps belong in an intent hash | Observation time is volatile and excluded; admissibility evidence remains included | rejected |
| A successful native task proves a backup | A new non-baseline canonical recovery point is mandatory | rejected |

| Unknown verification may be treated as success | Pending until verified, failed, or policy deadline becomes unknown | rejected |

## Residual risks accepted for V3.3

- No compatible Proxmox endpoint exists in the current staging inventory, so staging can prove schema, gates, API/UI, and non-Proxmox negative behavior but not execute a real disposable `vzdump` task. A Proxmox sandbox remains required before promoting the flag beyond canary.
- PVE storage-content inventory may expose verification later than task completion. The policy deadline makes this explicit but long deadlines prolong parent state.
- A provider clock skew greater than two minutes can delay discovery until unknown. Increasing the window without endpoint evidence would risk accepting unrelated points.
- PBS verification capability does not guarantee that `verify-new` or a verification job is configured. Required execution therefore waits for point-level evidence and may time out.
- Parent scheduling records failures in bounded application logs and immutable plan evidence; a dedicated backup SLO alert channel is part of later observability work.
- Cancellation of a provider-native task may be rejected after the task has committed. Reconciliation and point discovery remain the authority.
- The per-repository lock serializes backup submission to one operation at a time even when policy concurrency is greater than one for the same repository. This conservative control reduces provider/storage blast radius; finer repository concurrency needs real load evidence.
- Existing V3.2 plan hashes created before volatile observation time was removed should be replanned before execution. No existing plan is automatically upgraded.

## Promotion requirements

- run a disposable QEMU and LXC backup against a test PVE/PBS endpoint;
- confirm UPID restart recovery and cancellation behavior;
- observe point discovery and point-level verification transitions;
- test shared and node-local repositories;
- validate required token privileges without granting repository deletion;
- prove no prune/delete API call occurs with transport capture;
- keep the execution flag disabled on endpoints without that evidence.
